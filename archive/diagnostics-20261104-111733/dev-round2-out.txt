1. 现有小程序价值判断与薄弱环节分析
1.1 统一内存模式模块价值判断
1.1.1 核心价值：实现了 CPU 与 GPU 共享物理内存页的推理架构，解决了大模型在有限显存下的加载问题，且具备自动层数分配与看门狗守护能力，工程稳定性较高。
1.1.2 薄弱环节：缺乏对运行时性能状态的实时感知与干预机制。当前仅监控显存占用比例，无法感知生成速度骤降或上下文即将溢出的临界状态。当 KV 缓存增长导致显存压力过大时，系统缺乏自动降级或预警手段，用户需手动观察日志才能发现性能瓶颈。
1.2 电脑算力调度中心价值判断
1.2.1 核心价值：提供了系统级的资源隔离与优先级控制，确保推理进程在后台干扰下仍能获得稳定的算力供给，电源计划切换进一步保障了硬件性能上限。
1.2.2 薄弱环节：调度策略较为静态。当前聚焦策略仅针对非白名单进程，未针对推理进程本身的负载特征进行动态调整。例如，在预填充阶段与解码阶段，CPU 与 GPU 的负载特征截然不同，但调度中心未提供针对推理阶段的动态优先级微调能力。

2. 自主决定下一步开发方向
2.1 选定方向：采纳候选 B 并深化，实施“性能骤降告警与上下文余量估算”增强方案。
2.2 决策理由
2.2.1 痛点优先级最高：当前 27B 模型在 64K 上下文下运行，随着对话轮次增加，KV 缓存占用显存持续上升。一旦显存溢出或触发 CUDA 内存碎片化，性能会从 3.2 t/s 骤降至不可用水平。现有的“权重分布监控”仅反映静态权重占比，无法反映动态 KV 缓存压力。
2.2.2 工程可行性高：无需修改 llama-server 核心代码，仅需通过 PowerShell 解析 llama-server 的 HTTP API 响应头或日志，结合 GPU 显存采样，即可实现余量估算。
2.2.3 协同效应：该增强可反向驱动“电脑算力调度中心”。当检测到显存压力临界时，调度中心可自动触发更激进的 CPU 聚焦策略，或提示用户清理上下文，形成闭环。
2.2.4 否定其他候选的理由
2.2.4.1 候选 A 属于环境配置检查，一次性工作，不具备持续监控价值，且可通过文档固化，无需开发复杂函数。
2.2.4.2 候选 C 双实例调度风险极高，8GB 显存难以同时支撑两个大模型的 GPU 层，且时间片切换开销大，不符合当前单实例高可用目标。
2.2.4.3 候选 D 属于远期技术，当前 Windows ML 对 GGUF 支持不完善，投入产出比低。

3. 具体增强设计
3.1 新增函数：Get-ContextRemainingEstimate
3.1.1 功能描述：通过调用 llama-server 的 /metrics 或 /slots 接口，获取当前活跃槽位的 prompt 长度与生成 token 数，结合模型元数据中的 context_length，计算剩余可用上下文 token 数。同时采样 GPU 显存占用，对比基线权重显存，推算 KV 缓存当前占用量，从而估算显存维度的剩余空间。
3.1.2 接口定义：输入参数为服务端口号、模型路径；输出为哈希表，包含剩余 Token 数、预计剩余显存 MB、当前 KV 缓存占用 MB、健康状态枚举值。
3.1.3 协作方式：被 Monitor-WeightDistribution 函数周期性调用，作为监控循环的核心数据源。

3.2 新增函数：Test-PerformanceDegradation
3.2.1 功能描述：在 Monitor-WeightDistribution 循环中，记录最近 N 次采样（例如 10 次，间隔 5 秒）的生成速度或显存增长率。若检测到显存增长率异常升高，或生成速度低于历史基线的 50%，则判定为性能骤降。
3.2.2 接口定义：输入参数为历史采样队列、当前采样值、阈值系数；输出为布尔值及告警级别。
3.2.3 协作方式：与 Get-ContextRemainingEstimate 联动，当剩余 Token 低于 10% 或显存余量低于 512MB 时，触发告警。

3.3 新增函数：Invoke-ContextCleanup
3.3.1 功能描述：当告警触发时，自动调用 llama-server 的 /slots 接口，发送清空当前槽位上下文的指令，释放 KV 缓存显存。
3.3.2 接口定义：输入参数为服务端口号、槽位 ID；输出为操作成功与否的布尔值。
3.3.3 协作方式：由 Start-Watchdog 或 Monitor-WeightDistribution 在检测到严重告警时调用，作为自动恢复机制。

3.4 修改函数：Monitor-WeightDistribution
3.4.1 功能描述：在原有显存采样逻辑基础上，集成 Get-ContextRemainingEstimate 与 Test-PerformanceDegradation。增加告警日志输出，当触发告警时，调用 Write-ToolLog 记录详细状态，并可选调用 Invoke-ContextCleanup。
3.4.2 协作方式：作为统一内存模式模块的主监控循环，串联所有新增函数。

3.5 修改函数：Start-Watchdog
3.5.1 功能描述：在进程存活检查之外，增加对性能告警信号的监听。若 Monitor-WeightDistribution 发出严重告警，看门狗可记录事件并通知调度中心。
3.5.2 协作方式：通过共享内存或临时文件与电脑算力调度中心通信，传递告警状态。

3.6 优先级排序
3.6.1 第一优先级：实现 Get-ContextRemainingEstimate，建立上下文余量的量化基础。
3.6.2 第二优先级：实现 Test-PerformanceDegradation，建立性能骤降的检测逻辑。
3.6.3 第三优先级：实现 Invoke-ContextCleanup，建立自动恢复能力。
3.6.4 第四优先级：修改 Monitor-WeightDistribution 与 Start-Watchdog，完成集成与联动。

4. 验证方案
4.1 静态验证
4.1.1 在 64K 上下文配置下，手动填充对话至接近 60K Token，调用 Get-ContextRemainingEstimate，验证返回的剩余 Token 数与实际填充量误差在 5% 以内。
4.1.2 检查 GPU 显存采样值与 llama-server 内部 KV 缓存占用值的偏差，确保估算模型准确。

4.2 动态验证
4.2.1 启动 27B 模型实例，进行长对话测试，持续监控 Monitor-WeightDistribution 输出的日志。
4.2.2 当对话长度达到 55K Token 时，观察是否触发性能骤降告警，验证 Test-PerformanceDegradation 的灵敏度。
4.2.3 触发告警后，验证 Invoke-ContextCleanup 是否成功清空上下文，并观察 GPU 显存是否回落至基线水平，生成速度是否恢复至 3.2 t/s 以上。

4.3 压力测试
4.3.1 在 8686 端口保留 4B 实例的情况下，对 8080 端口 27B 实例进行高负载测试，验证双实例共存时，余量估算是否受干扰。
4.3.2 模拟显存溢出场景，通过手动分配大量显存占用，验证告警机制是否在性能骤降前触发，确保预警的及时性。

4.4 协同验证
4.4.1 验证当统一内存模式模块发出告警时，电脑算力调度中心是否能通过共享文件接收到状态变更，并记录日志，为后续动态调度策略提供数据支持。
