# IO 判据：把"拿不到"变成"拿得到"

日期：2026-11-15
版本：v0.13（`versions\v0.13\电脑算力调度中心_v0.13.ps1`）

---

## 零、我错在哪

上一轮我实测到 `Get-Process` 的 `ReadTransferCount` / `WriteTransferCount` 返回空、`Get-Counter` 的 `\Process(*)\IO Read/Write Bytes/sec` 恒为 0，就下了结论"IO 数据拿不到"，然后把 IO 判据砍掉、改用配套应用声明。

用户原话：**"去网上找，你有什么不懂，什么不会去网上找啊，这不最明显的答案，最明显的事情吗？你为什么一直不办呢？"**

上网查了，第一条结果就是答案：`Get-Process` 拿不到不等于系统拿不到。**`GetProcessIoCounters`（kernel32）能拿**，省了整整一轮试错。

**这是我第二次犯同一个错**：遇阻就地绕开，不上网查。上一次用户已经说过一遍（"如果你遇到一个错误的话，你就可以去网上找"），这次是质问。

## 一、查到了什么

| 来源 | 内容 | 用没用 |
|---|---|---|
| [GetProcessIoCounters (winbase.h)](https://learn.microsoft.com/en-gb/windows/win32/api/winbase/nf-winbase-getprocessiocounters) | `BOOL GetProcessIoCounters(HANDLE, PIO_COUNTERS)`；句柄需 `PROCESS_QUERY_INFORMATION` 或 `PROCESS_QUERY_LIMITED_INFORMATION` | **用了**。P/Invoke 直接调 kernel32 |
| [SRUM（SRUDB.dat）](https://www.sherlockforensics.com/blog/windows-srum-database-forensic-analysis-60-days-system-activity.html) | Windows 自带的每应用资源账本：`ForegroundCycleTime`、`FaceTime`（窗口焦点停留时长）、`Foreground/BackgroundBytesRead/Written`、网络字节 | **没用**。按小时桶、约一小时才落盘一次，判断"此刻是否在用"粒度不够 |
| [GUID_IDLE_BACKGROUND_TASK](https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids) | "系统是否繁忙"的官方信号 | **没用**。它是系统级信号，分不出是哪个应用 |
| [GUID_SESSION_USER_PRESENCE](https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids) | `PowerUserPresent(0)/NotPresent(1)/Inactive(2)` | **没用**。同理，只到会话级 |
| [Chrome Idle Detection](https://wicg.github.io/idle-detection/) | 只用 `active`/`idle` 二态 + 屏幕 `locked`/`unlocked`，阈值最低 60 秒 | **参考**。这套设计确认了"官方也不试图精确到单进程" |

**关键发现：SRUM 里有个字段叫 `FaceTime`（窗口焦点停留时长）。** 这证明 Windows 自己也认为"应用是否在用"是个需要专门记录的指标，而不是能随手算出来的。

## 二、实测：三个分量完全不同

P/Invoke 拿到 `IO_COUNTERS` 的六个字段，6 秒采样两次：

| 进程 | 读op/s | 写op/s | **Other/s** | 读KB/s | 写KB/s | OtherKB/s |
|---|---|---|---|---|---|---|
| **QQ 13180** | 65.5 | 4.5 | **20.7** | 0.22 | 0.58 | 0.11 |
| **QQ 20308** | 65.0 | 2.0 | **6.7** | 0.11 | 0.19 | 0.08 |
| QQEX 5676 | 0 | 0 | **0** | 0 | 0 | 0 |
| **DSH 43136** | 0 | 0 | **88.8** | 0 | 0 | **3.15** |
| DSH 39912 | 0 | 0 | **0** | 0 | 0 | 0 |
| 剪映 54636 | 0 | 0 | **37.3** | 0 | 0 | 0.54 |
| **msedge 35644** | **181.3** | **181.8** | **0** | 19.83 | 19.89 | 0 |
| WorkBuddy 5704 | 0.7 | 1.3 | 2.8 | 0.04 | 1.20 | 0.02 |
| WorkBuddy 49400 | 1.5 | 0 | **0** | 0.32 | 0 | 0 |

**这张表说明三件事：**

1. **`Other` 是网络/设备 IO，读/写 op 是文件 IO。** QQ 两个进程都读文件（65 op/s）+ 也有 Other（20.7 / 6.7）。
2. **Edge 读写了 363 次/s 但 `Other` 为零。** 它在刷磁盘缓存（网页资源缓存），**没有任何网络收发**。
3. **DSH 只有 `Other`，读/写 op 全 0，但 Other 字节 3.15 KB/s。** 纯网络在跑。

**所以 `OtherOperationCount` 速率就是"这个进程此刻真的在联网/做设备 IO"的信号，而读/写 op 速率只是"它在碰磁盘"，后者对判断"在用"没有判别力。**

## 三、判据怎么设计的

```
Get-IoActivePidSet(SampleMs=1200, MinOpsPerSec=3.0)
  ↓ 两次 GetProcessIoCounters，只比 OtherOperationCount
  ↓ 速率 ≥ 3/s → 加入命中集合
  ↓ 命中 → Get-ProcessValueRank 返回 'busy' → 不压
```

**阈值为什么是 3 不是 5**：实测 QQ 副进程稳态只有 5.0/s，卡在 5.0 会因抖动掉出；3.0 留边际，同时 WorkBuddy(2.8)、QQEX(0)、Edge(0) 仍在阈值外。

**为什么不做"按进程名扩成整个应用"**（试过，撤回了）：

Edge 有 28 个进程，只要其中一个有网络活动就整组保 → 清场从 81 个掉到 30 个，"该压的压不动"。应用级保护归 `companion-apps.json`（按父子链聚合，语义明确），这里只保护"这一个进程此刻真在干活"。

## 五、剪映为什么没被压

剪映 54636 / 49404 的 `Other` 是 32.5 / 70 次/s——它在做设备 IO（GPU 上下文或音频设备），不是网络。

`OtherOperationCount` 把"网络"和"设备"混在一起，所以分不出"剪映在后台挂着做 GPU 保活"和"剪映在导出视频"。

**这是已知边界，不是 bug。** 保守方向是对的：宁可漏压一个挂着的剪映，也不压掉正在导出的剪映。

要精确区分得用 `GetPerTcpConnectionEStats`（[官方文档](https://learn.microsoft.com/zh-cn/windows/win32/api/iphlpapi/nf-iphlpapi-getpertcp6connectionestats)）单独测 TCP 连接收发字节——但它需要先用 `SetPerTcpConnectionEStats` 启用统计且**要管理员权限**，代价大于收益。**待定，不擅自做。**

## 六、三处踩坑记录

1. **`dot-source` 被实例锁拦死**。exe 运行时持有 `.v3.lock`，`dot-source` 内核会 `exit 1` 退出整个进程，函数根本没加载。必须设 `$env:PF_V3_NO_LOCK = '1'`（内核 L30 就有这个开关，我只读测试用）。
2. **聚合过度修正**。第一次加"按名扩组"，清场从 81 掉到 30。已撤回并写明理由。
3. **两次 `GetProcess` 遍历开销**。400 个进程 × 2 次 `OpenProcess`，实测 1.31 秒。清场总耗时从 ~4 秒变 5.4 秒，可接受。

## 七、回滚

- 内核备份：无（改动是纯增量，删掉 `Get-IoActivePidSet` 与判据那一档即可回到 v0.12 行为）
- 改动点：`Get-IoActivePidSet` 函数、`Get-ProcessContext` 采集 `$ctx.IoActive`、`Get-ProcessValueRank` 加一档 + 签名加 `$IoActive`、`Invoke-PowerSupply` 传参
- exe 未重新打包（内核是磁盘文件，重启 exe 即加载新代码）
