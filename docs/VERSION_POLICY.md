# PowerFocus 版本规则（Version Policy）

> 生效日期：2026-11-14。本文是「每次开发完如何汇集成一个版本」的唯一约定，
> 与 `CHANGELOG.md` 的「版本真源」条款配套，冲突时以本文的版本号判定为准。

## 1. 唯一对外版本号

- 唯一对外版本号 = **GitHub Release tag**，形如 `v0.11.0`，遵循 SemVer 2.0.0。
- `product/v1.00` 是代码目录名与数据目录槽，`versions/current.json` 是内核迭代槽，
  `mcp-server.py` 里的 `SERVER_VERSION` 是协议实现内部编号——**这些都不是发布版本**。
- 0.x 阶段遵循 SemVer 惯例：`0.x` 不承诺稳定接口，但仍按下列规则递增，便于用户判断变更量级。

## 2. 小更新 / 功能版本 / 全面更新

用户口径：「小版本是小更新，大版本是全面更新」。为避免只有两级导致语义含糊，
落地为 SemVer 三段，并把「小 / 大」明确对应到用户的说法：

| 用户说法 | 段位 | 判定标准（满足任一即升该段） | 例子 |
|---|---|---|---|
| **小版本 / 小更新** | `PATCH`（`0.10.2 → 0.10.3`） | 修 bug、文档与教程、CI 与依赖、内部重构、测试补充；**不改变对外接口、不新增能力、不需要用户改配置** | 修回执时间戳、加 6 个单测、补 LICENSE 附件 |
| **功能版本**（中等更新） | `MINOR`（`0.10.2 → 0.11.0`） | 新增向后兼容的能力或发行物、新增 API / 工具 / 页面、新增可选配置；老用法继续有效 | 新增 MCP Server、新增只读接口、新增主题 |
| **大版本 / 全面更新** | `MAJOR`（`0.x → 1.0.0`） | 不兼容的接口或配置变更、架构重写、产品定位或形态变化、删除既有能力、要求用户迁移 | 切换 stable 内核到 v0.10、命令总线换成新协议、放弃旧 exe |

补充规则：

- 一次发布同时含多类变更时，**按最高段位升一级**，不叠加（例如含新能力又修 bug → 只升 MINOR）。
- 纯证书 / 附件 / README 修补，不改代码 → PATCH；若只是补传已有 tag 的附件、源码未变，**不新增版本号**（避免「同一附件归属两个版本」）。
- `1.0.0` 作为「全面更新」的门槛：只有在内核转正、对外接口冻结、安装与回滚流程完备后才可使用；当前 0.x 不跳级。
- 预发布用 `-rc.1` / `-beta.1` 后缀，正式版去掉后缀。

## 3. 每次开发完成的固定动作（发布闭环）

开发告一段落必须依次完成，不允许「代码改了但没版本」：

1. **判定段位**：对照第 2 节表格，写在提交信息里。
2. **同步 `CHANGELOG.md`**：把 `[Unreleased]` 内容归入新版本段，保留未做完项。
3. **本地验证**：pytest、ruff、py_compile、`.ps1` 语法、JSON/YAML 契约、源码实机 `/api/health`。
4. **重新打包 exe**（凡改了 `product/v1.00/app/` 下的代码或 `app/web/` 静态资源就必须重打，
   否则用户双击的仍是旧快照——这是 2026-11-14 已经踩过一次的坑）。
5. **打 annotated tag 并推送**，tag 与源码 commit 一一对应。
6. **创建 Release 并上传附件**：exe、`LICENSE`、`THIRD_PARTY_NOTICES.md`，以及本版本的附加发行物（见第 4 节）。
7. **确认 CI 全绿**，记录 exe 的字节数与 SHA256 到 CHANGELOG。
8. **日志留痕**：追加到工作区 `.workbuddy/memory/YYYY-MM-DD.md`。

## 4. MCP 发行物与主版本的对齐

用户口径：「专门搞一个版本做成 MCP，直接对标最新的版本」。

- MCP Server 作为**独立发行物**放在 `mcp/`，可脱离主仓库单独拷贝给任何 AI 客户端加载。
- MCP 发行物**不另起一套版本号**，其版本始终等于它所对齐的主应用 Release 版本。
  例：主应用 `v0.11.0` → MCP 发行物 `PowerFocus-MCP-v0.11.0.zip`，内部 `VERSION.json` 写
  `{"mcp_version":"0.11.0","target_app_version":"0.11.0"}`。
- 「对标最新版本」的含义：MCP 声明自己适配哪个主应用版本；主应用升 MINOR/MAJOR 时，
  MCP 必须同步升到同一版本并复测；纯 PATCH 且不影响 MCP 所调用接口时可只更新 `tested_app_versions` 列表。
- 每次发版把 `mcp/` 打成 zip 作为该 tag Release 的独立附件，与 exe 并列。
- MCP 协议版本（如 `2026-07-28`）是**协议兼容声明**，不是产品版本号，写进 `VERSION.json` 的
  `protocol_versions`，不要与 `mcp_version` 混淆。
