# 04 · 架构师（沈工）：接口清算与预留设计

> 本轮性质：P0 集团级推演，只出方案不改代码。未改动任何 `.ps1/.py/.exe/.json`，未 kill 进程。
> 取证范围：`server.py`（L160–1168）、`bus.py`、`bus_receipt.py`、内核 `v0.13.ps1`（L128–151、L1639–1669、L2195–2331）、`app.js`（L129–160、L377–405）、`commands/{in,out,done}` 实测目录。
> 未读部分按底稿 §7 标注"未读/未证实"，不补全想象。

## ① 一句话结论

**现有三层契约是"文件命名对齐 + 纯文本回执"的弱契约；第二步所需的请求级追踪、结构化结果与调度元数据，可以在不改总线协议（目录、文件名、回执文本格式）的前提下，靠命令 JSON 加可选键、回执并行加可选 JSON 来预留；第一步只写不读，代价极小。**

### B. API ↔ 总线（文件 JSON）

- **写入**：`BusClient.call`（`bus.py` L57–103）。目录 `KERNEL_DIR/commands/in`；文件名 `ui-<毫秒>-<进程序号>-<6位随机>.json`；`.tmp → os.replace` 原子写。
- **命令 JSON 字段**：`action` + 业务参数；`token`（`bus_call` L736 服务端注入内核令牌，客户端无法覆盖）；`idempotency_id`（L65 缺省 = 文件 id）。服务端剥除客户端自带的 `token`/`idempotency_id`（`server.py` L967–968）。
- **回执**：`done/{id}.json.result.txt`，纯文本；`bus_receipt.parse_receipt`（L17–36）剥首行时间戳，正文 `ERROR:` 开头判失败，空文件最多再等 3 轮。
- **超时**：默认 30s；`/api/command` 夹紧 `[1,600]`；router 20s、boost 60s。超时后删除 in 命令；晚到的孤儿回执靠 GC（600s 节流，done 内 24h 超龄清理）回收。
- **幂等/确认**：幂等键已下发但**内核忽略未知字段**（`bus.py` L60–61 注释）；回执无结构化确认状态。

### C. 总线 ↔ 内核

- **轮询**：`Forms.Timer` 2000ms（内核 L2317–2323），扫 `in/*.json`，按 `LastWriteTime` 排序，单线程 `foreach` 串行处理，`BusyProcessing` 挡下一 tick（L2245–2279）。
- **鉴权**：`ConvertFrom-Json` 后比对 `$cmdObj.token -ne $expected`，失败回 `ERROR: 命令总线认证失败`（L2255–2257）。
- **分发**：`Invoke-CommandObject`，`switch($Cmd.action)`，default → `ERROR: 未知 action: <action>`（L1641、L2208–2210）。
- **结果落盘**：`.tmp` 再 `Move-Item` 到 `done/{文件名}.result.txt`；命令副本一并 `Move` 到 `done/{文件名}.json`（L2268–2273）。
- **心跳**：`v3_heartbeat.json`，服务端以 15s 内为活（`server.py` L752–758）。
- **全局状态**：`status` 动作覆写 `out/status.json`（L1647–1652），是全局快照，**不是某条命令的请求级结果**。

## ③ 总线结构性缺陷清单（每条挂证据）

1. **令牌失败只有纯文本，无错误码、无重试通道**
   - 证据：`v3.log:422-423` "命令总线认证失败：缺少或错误的内核授权令牌"；代码内核 L2255–2257。
   - 结构原因：令牌是命令 JSON 内一个明文字符串，内核只做字符串相等比对；失败结论只能塞进回执正文。
   - 不动它的后果：前端无法区分"令牌文件缺失/过期/被篡改"，也无法触发重新 bootstrap；同类故障只能人工看日志。

2. **action 空值/未识别，失败信息为空**
   - 证据：`v3.log:328/330` "未知 action:" 后为空。
   - 结构原因：action 直接取 JSON 体字符串，`switch` default 只回纯文本；命令封装层未在入口校验 action 非空。
   - 未证实说明：v0.13 代码**不按文件名解析 action**（取自 `$Cmd.action`）；底稿"文件名含空格导致解析失败"这一因果在本版代码中未证实，可能是旧版本行为或 JSON 体损坏，需数据分析师复核日志所属版本。
   - 不动它的后果：坏命令静默落 done，无 schema 校验层，第二步无法自动分类。

3. **结果与命令无状态机关联，回执是纯文本**
   - 证据：实测 done 目录残留 **200 个**成对文件（命令副本 + `.result.txt`）；成败只靠正文 `ERROR:` 前缀判定（`bus_receipt.py` L14、L34）；回执无 status/request_id/error_code 字段。
   - 结构原因：协议靠"文件名对齐"做关联，文件系统一致性靠 `.tmp` 补救；没有请求级状态字段。
   - 不动它的后果：孤儿回执只能等 24h GC；任何一条命令都无法按请求追踪生命周期。

4. **无背压：单线程串行，无队列深度与并发上限**
   - 证据：内核 L2247 `foreach` 全量处理；L2278 `BusyProcessing` 标志；in 目录对本机任意进程可写。
   - 结构原因：轮询 + 串行执行模型，没有队列长度、优先级、并发槽位概念。
   - 不动它的后果：长尾命令阻塞后续全部命令；突发多条时排队抖动，2s 轮询放大延迟。

5. **无命令级超时与重试：服务端撤回 ≠ 内核停止**
   - 证据：`bus.py` L97–103 注释"若内核稍后才完成，其孤儿回执由 GC 回收"；内核 tick 内未见命令执行超时包裹（逐条 action 实现未读，§7-2）。
   - 结构原因：超时判定在服务端，执行超时在内核侧缺位；两边状态互不可见。
   - 不动它的后果：用户看到"超时失败"，动作可能稍后才生效，系统状态不可观测、不可回滚。

6. **固定 2s 轮询，无事件通知、无优先级**
   - 证据：内核 L2320 `Interval = 2000`。
   - 结构原因：Timer 轮询模型；命令到达后要等下一个 tick。
   - 不动它的后果：最短命令也有最长 2s 等待；高负载下响应不稳，调度场景无法插队。

7. **回执无耗时/失败码/版本，观测数据不规范**
   - 证据：回执纯文本（L2269–2273）；同类数值不规范化问题见 `mem-guard.log:19` 浮点直打 `357.09999999999997`。
   - 结构原因：结果层只传正文，不产出度量字段。
   - 不动它的后果：第二步做热感知/多引擎选择时，拿不到耗时、错误分类、内核版本做决策。

8. **多实例无隔离标识**
   - 证据：底稿 §2.4 九份副本哈希两两不同；总线目录按 `KERNEL_DIR` 解析。
   - 结构原因：命令与回执都不带实例/引擎标识。
   - 不动它的后果：第二步多引擎并行时，回执可能被错配实例取走。

## ④ 第二步能力清单（多引擎 / 热感知调度 / 更稳执行）

| 能力 | 当前是否具备 | 用途 |
|---|---|---|
| 请求级关联 ID 全链路回链 | 否（idempotency_id 未被消费） | 追踪、去重、孤儿回执归属判定 |
| 结构化结果：状态 / 失败码 / 耗时 / 内核版本 | 否 | 失败分类、重试决策、观测 |
| 调度元数据：目标引擎、优先级 | 否 | 多引擎路由、排队插队 |
| 命令级超时契约与回执三态（成功/失败/超时未执行） | 部分（仅服务端超时） | 状态可见、可回滚 |
| 背压信号：队列深度、心跳版本 | 否 | 负载感知、拒绝/排队 |
| 执行来源与时间戳留痕 | 否 | 审计与回放 |

**能否不改总线协议预留？能。** 目录约定（in/out/done）、文件命名（`{id}.json` / `{id}.result.txt`）、回执纯文本格式全部保留；只在命令 JSON 加可选键（旧内核只取具名属性，未知键忽略，见 `bus.py` L60–61 注释）；结果侧并行写可选 JSON 侧车文件，第一步服务端不读。

## ⑤ 预留字段清单表

### 命令 JSON（`in/{id}.json`，可选键，第一步只写不读）

| 字段 | 类型 | 缺省值语义 | 第一步行为 | 第二步启用条件 |
|---|---|---|---|---|
| `request_id` | string | 缺省复用现有 `idempotency_id`，不新增生成器 | 服务端写入；内核忽略 | 内核/回执回带同一 ID，服务端按 ID 关联回执 |
| `deadline_ms` | int \| null | `null` = 沿用现有 30s 超时 | 仅服务端自用；内核忽略 | 内核据此判定"超时未执行"并回三态回执 |
| `priority` | string enum `normal`/`high` | `normal` | 写入但不参与排序 | 调度器按优先级排队/插队 |
| `engine_target` | string | `auto` | 写入但不路由 | 多引擎实例就绪后按值分发 |
| `trace` | object `{source, ts}` \| null | `null` | 记录来源与落盘时间 | 观测/审计链路消费 |

命令 JSON 示例（第一步形态）：

```json
{
  "action": "set_priority",
  "process_name": "python",
  "priority": "BelowNormal",
  "token": "<服务端注入，不进 HTTP 响应>",
  "idempotency_id": "ui-1732000000000-1-a1b2c3",
  "request_id": "ui-1732000000000-1-a1b2c3",
  "deadline_ms": 30000,
  "priority": "normal",
  "engine_target": "auto",
  "trace": { "source": "web", "ts": "2026-11-19T22:00:00+08:00" }
}
```

### 结果侧（`done/` 目录，可选侧车文件 `{id}.result.json`，第一步不写不读）

| 字段 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `request_id` | string | 回链命令 ID | 关联主键 |
| `status` | enum `ok`/`error`/`timeout` | 无 | 三态，替代纯文本前缀猜测 |
| `error_code` | string \| null | `null` | 机器可读失败分类 |
| `elapsed_ms` | int \| null | `null` | 执行耗时 |
| `kernel_version` | string | 无 | 执行实例版本 |
| `engine` | string \| null | `null` | 实际承接引擎 |

侧车示例：

```json
{
  "request_id": "ui-1732000000000-1-a1b2c3",
  "status": "ok",
  "error_code": null,
  "elapsed_ms": 412,
  "kernel_version": "v0.13",
  "engine": "auto"
}
```

> 兼容规则：旧回执 `{id}.result.txt` 保持原格式；`bus_receipt.gc_done` 已同时遍历 `*.result.txt` 与 `*.json`（L72），侧车文件天然纳入 GC。第二步启用前，服务端解析路径一行不改。

**第一步只写不读的代价**：命令文件略增几个键；侧车文件在旧内核下不存在（无副作用）；主要风险是**误用**——开发误以为第二步已启用，去消费尚未产生的字段。对策：字段名在第一步文档中标注 `reserved`，代码注释注明"第二步启用前不读"。

## ⑥ 加与不加的代价对比

口径：改动文件数 / 停服分钟 / 回归面。估算均为**假设**（未做实际工作量测量）。

| 方案 | 改动文件数（假设） | 停服（假设） | 回归面 |
|---|---|---|---|
| **第一步预留字段**（写入不读，协议不动） | 3：`bus.py`（生成键）、`bus_receipt.py`（侧车识别/GC）、`server.py`（透传）；内核 0 改动 | 0：向后兼容，FastAPI 可滚动重启；旧内核无需替换 | 命令写入路径 + GC；回执解析路径不动。用例：下发一条命令、解析一条回执、GC 一轮 |
| **第二步再改协议** | 6+：`bus.py`、`bus_receipt.py`、`server.py`、内核分发、前端 `runCommand`、接口文档；新旧内核并存期需双写两种回执 | 内核与服务端须同时升级；单台桌面工具替换进程估计 10–30 分钟；九份副本要同步对齐 | 全链路：下发、回执解析、前端错误提示、多实例兼容；旧纯文本与新结构化回执要双解析，并存期长期维护两套解析 |

## ⑦ 架构红线（第二步绝对不能碰的三样）

1. **不改目录与文件命名约定**：`commands/{in,out,done}`、`{id}.json`、`{id}.result.txt`。这是九份旧内核与桌面启动判定的共同契约；改名或改目录等于同时打破新旧两代，回滚成本极高。
2. **不把内核令牌带出服务端/HTTP 响应**：令牌只在 `bus_call` 服务端注入（`server.py` L720、L736）。第二步多引擎也必须沿用此边界，不允许前端、引擎进程或回执日志自行持有或回显令牌。
3. **不为未来多引擎提前引入消息队列/总线抽象中间件**：当前单机文件总线满足当前需求；第一步补字段，第二步验证真实瓶颈后再谈替换。提前上抽象层是过度设计，直接抬高运维复杂度并割裂旧内核兼容。

## ⑧ 对其他岗位的质疑

1. **对产品/前端**：`/api/command` 现在只有纯文本失败信息。第二步若要按 `error_code` 做差异化提示，前端必须先定义错误展示契约；否则预留的 `error_code` 落不了地，字段白加。
2. **对 DevOps/运维**：九份内核副本、三套版本号并存（底稿 §2.3、§2.4）。预留字段虽向后兼容，但在启用 `request_id` 回链前，必须先冻结"当前到底哪个内核实例在跑"，否则回执归属无法判定，多引擎会互相抢单。
3. **对 CTO**：第二步多引擎调度是否真需要新总线，还是先在现有命令上加 `engine_target` 路由即可？需求未证实，不要先采购中间件或定微服务边界。

## ⑨ 我可能错在哪

1. **内核命令级超时是否真缺位**：我只读到 tick 与分发结构，未逐条读每个 action 的实现（底稿 §7-2）。若部分 action 内部已有超时包裹，缺陷 5 的"内核侧无超时"描述需按实现修正。
2. **L1170 之后的服务端路由未读**：`/api/audit`、`/api/settings`、`/api/bootstrap/*`、`/api/cloud/test` 等接口的入参校验、错误码与鉴权方式我未逐段核实；本轮清算表对这些接口标"未证实"，结论不得外推。
