# 05 · 开发工程师（小马）：四个现场 bug 的根因与可落地改法

> 本轮性质：P0 集团级推演，**只出方案不改代码**。未修改/删除任何 `.ps1/.py/.exe/.json`，未 kill 进程，未写 versions 与 product。
> 取证范围：内核 `versions\v0.13\电脑算力调度中心_v0.13.ps1`（2568 行，131,432 B）、`rules-engine.ps1`、`product\v1.00\app\server.py` / `bus.py` / `bus_receipt.py`、`commands\done` 留存的失败/成功命令原件、`v3.log` 全文 478 行。
> 纪律：行号均为实测 grep/Read 所得；仓库内未定位到的生产者脚本标注"未证实"，不编函数名。

## ① 一句话结论

四个 bug 里，**两个是"命令没被执行"的功能性阻断（action 空值、令牌缺失），两个是"功能降级 + 日志噪声"的边缘问题**；内核侧解析链路本身基本可靠，真正的脏封装来自总线外部的生产者，内核能做的是兜底报错更清楚、失败分级更克制，而不是替生产者擦屁股。

## ② 四个 bug 逐条

### Bug 1：命令文件名带空格 → "未知 action"（v3.log:328/330）

**根因（已取证）**

- 内核总线轮询 `Invoke-CommandBusTick`（L2245–2251）：`Get-ChildItem -Filter *.json` → `Get-Content -Raw | ConvertFrom-Json`；action 取值在 `Invoke-CommandObject` L1641：`$action = [string]$Cmd.action`，**只认 JSON 正文的 `action` 字段**。
- 全脚本 grep 无 `BaseName`/文件名解析；文件名只用于回执命名（L2269/2273/2275）。**文件名与正文不一致时不存在"谁优先"，因为文件名压根不参与解析**。空格本身不破坏读取：`Get-ChildItem` + `-LiteralPath` 对空格路径无问题。
- 失败原件（`done` 留存）：`prio_37608_s1b set_priority BelowNormal.json` 正文为 `{"action": null, "pid": 37608, "priority": null, "token": "e776…"}`——**action 和 priority 被塞进了文件名，正文留 null**；改名重投的 `prio_37608_s1c.json` 正文带 `"action": "set_priority"` 即成功（v3.log:331–333）。
- 生产者定位：`BusClient` 文件名规则是 `ui-<毫秒>-<序号>-<6位随机>.json`（`bus.py` L33–36），两个失败文件名均不匹配；仓库内 `tests/probe-v3-actions.ps1` 等脚本也不生成此类命名。**外部临时脚本/手工投递，具体生产者未证实**。

**改法**：双保险。生产者侧立规范——文件名只做 ID（无空格、无业务参数），action/参数一律进 JSON 正文；内核侧加空值防御，不再落 `default` 报空串。

**改前**（L1639–1642）：

```powershell
function Invoke-CommandObject {
    param($Cmd)
    $action = [string]$Cmd.action
    Write-Log "INFO" "命令总线收到 action=$action"
```

**改后**：

```powershell
function Invoke-CommandObject {
    param($Cmd)
    $action = [string]$Cmd.action
    Write-Log "INFO" "命令总线收到 action=$action"
    if ([string]::IsNullOrWhiteSpace($action)) {
        return "ERROR: 命令缺少 action 字段（action 只取 JSON 正文，文件名不参与解析）"
    }
```

**为什么不引入文件名回退**：回退等于鼓励"参数写文件名"的脏封装，两套取值规则会让后续维护者猜不透谁优先；内核已经有 JSON 正文这一条契约，守住即可。

**验证**：在 `commands/in` 投一条正文 `"action": null` 的临时 JSON；期望回执为 `ERROR: 命令缺少 action 字段…`，且日志不再出现 `未知 action: ` 空串。再投一条正常 `set_priority` 确认主链路不变。
**回滚**：删掉新增的 `if` 块即恢复原样；改动仅限 L1641 之后三行，无共享状态。

### Bug 2：命令总线认证失败（v3.log:422–423，"缺少或错误的内核授权令牌"）

**根因（已取证）**

- 内核校验 L2255–2257：`$expected = Get-AuthToken`；`-not $expected -or [string]$cmdObj.token -ne $expected` 即拒绝。`Get-AuthToken`（L1432–1434）**每次实时读 `.auth_token` 并 Trim，无内存缓存**。
- 令牌生成 L1376–1378：**仅当文件不存在时** `NewGuid().ToString("N")` 写入；重启不重生成（全脚本仅 L1377 一处写 TokenFile）。
- 服务端 `_kernel_token()`（`server.py` L719–724）：每次 `TOKEN_FILE.read_text(encoding="utf-8-sig").strip()`，**同样无缓存**；`bus_call`（L735–736）给每条命令注入 `payload["token"]`；`/api/command` L967 先剥掉客户端自带 token。
- 失败原件 `setprio_s3_46316.json`：`{"action":"set_priority","priority":"BelowNormal","pid":46316}`——**根本没有 token 字段**；成功原件 `p_s3_46316.json` 带 token。实测当前 `.auth_token` = `e7760fcb1c7c42abab7fa326fccdedcf`（32 位 hex），与成功文件一致，**令牌未被重生成、未漂移**。
- 任务假设的"内核重启重生成令牌、server 缓存旧值"在当前代码里**不成立**：服务端不缓存、内核不重启重生成。真实不一致场景：(a) 生产者漏填 token（本次实测命中）；(b) 外部生产者缓存了旧令牌，而令牌被删后重建；(c) 令牌 ACL（L1384）只授当前用户 R，服务端以别的账户运行时读不到，`_kernel_token()` 静默返回 `""`。

**改法**：内核回执把"缺字段"和"不匹配"分开，便于一眼定位是漏封装还是令牌漂移；服务端读不到令牌时留审计痕迹（当前静默 `""`）。**不做旧令牌宽限**——那是安全边界，不能破。

**改前**（L2255–2260）：

```powershell
$expected = Get-AuthToken
if (-not $expected -or [string]$cmdObj.token -ne $expected) {
    $resultText = "ERROR: 命令总线认证失败：缺少或错误的内核授权令牌"
} else {
    $resultText = Invoke-CommandObject $cmdObj
}
```

**改后**：

```powershell
$expected = Get-AuthToken
$hasToken = $cmdObj.PSObject.Properties.Name.Contains('token') -and
            -not [string]::IsNullOrWhiteSpace([string]$cmdObj.token)
if (-not $expected) {
    $resultText = "ERROR: 内核授权令牌缺失：.auth_token 未生成或不可读"
} elseif (-not $hasToken) {
    $resultText = "ERROR: 命令未携带内核授权令牌（token 字段缺失）"
} elseif ([string]$cmdObj.token -ne $expected) {
    $resultText = "ERROR: 命令总线认证失败：内核授权令牌不匹配"
} else {
    $resultText = Invoke-CommandObject $cmdObj
}
```

服务端 `server.py` L719–724 配套：`except OSError` 分支除返回 `""` 外，调一次 `security.audit` 留痕（具体审计函数名沿用 L738 已有 `security.audit` 用法，未逐行读 security.py，**审计字段细节未证实**）。

**验证**：分别投三条——无 token 字段、token 为空串、token 为错误 hex；期望回执分别对应上面三种文案，互不混淆；再投一条带正确令牌的命令确认放行。
**回滚**：还原 L2255–2260 原判断表达式；服务端审计行单独回退，不影响总线主路径。

### Bug 3：EcoQoS PID 竞态（v3.log:36/56/87/119/150，PID 47596 反复失败）

**根因（已取证）**

- 补给路径 `Invoke-PowerSupply`：L601 `$procs = Get-Process` **一次性快照**，L608 遍历，L630 调 `Set-EcoQos`；`rules-engine.ps1` L191–206 内 `Get-Process -Id $ProcId -ErrorAction Stop`，进程已退出则 catch → WARN `EcoQoS 失败($ProcId): $_`，返回 `$false`。
- 快照到执行之间是 TOCTOU：进程在轮到它之前退出。同一 PID 47596 跨四个补给周期复现，最可能是**短命子进程被 OS 复用 PID**；但失败分支没记进程名，当时进程清单快照未留存，**成因属推断，未坐实**。L56 的 62052 则是补给到释放之间退出。
- 现有代码本来就**没有重试**；失败 PID 不记入 `PowerEcoQos`（L631 仅成功才记），释放路径不会再碰它，无泄漏。

**推荐方案：设置前重新取进程，取不到即跳过，不重试。** 理由：短命进程不会在几十毫秒内回来，重试只会拉长补给循环、多打 1–2 条 WARN，让日志更脏；复查一次 PID 成本极低，且能把"良性退出"和"权限拒绝"分开。

**改前**（`rules-engine.ps1` L191–206）：

```powershell
function Set-EcoQos {
    param([int]$ProcId, [bool]$On)
    try {
        $p = Get-Process -Id $ProcId -ErrorAction Stop
        $state = New-Object PowerFocus.RulesNative+PROCESS_POWER_THROTTLING_STATE
        ...
    } catch {
        Write-RuleLog "WARN" "EcoQoS 失败($ProcId): $_"
        return $false
    }
}
```

**改后**（进程退出前置复查，静默跳过；权限类失败仍留 WARN）：

```powershell
function Set-EcoQos {
    param([int]$ProcId, [bool]$On)
    $p = Get-Process -Id $ProcId -ErrorAction SilentlyContinue
    if (-not $p) { return $false }   # 进程已退出：TOCTOU 良性跳过，不重试、不打 WARN
    try {
        $state = New-Object PowerFocus.RulesNative+PROCESS_POWER_THROTTLING_STATE
        ...
    } catch {
        Write-RuleLog "WARN" "EcoQoS 失败($ProcId): $_"   # 仅受保护/权限问题保留
        return $false
    }
}
```

**验证**：起一个秒退的测试子进程，在其退出窗口内触发一次补给；期望日志不出现该 PID 的 WARN，释放路径不报残留；再对一个受保护系统进程开 EcoQoS，确认 WARN 仍保留。
**回滚**：把入口复查两行删掉、`Get-Process` 移回 `try` 内即可；`rules-engine.ps1` 是独立文件，不动内核主脚本。

### Bug 4：I/O 优先级权限不足（v3.log:175）与电源计划失败（v3.log:177–178、192–193）

**根因（已取证，两条分开判）**

*I/O 优先级*：`Set-IoPriority`（L730–739）走 `NtSetInformationProcess`（0x21），失败统一返回 `$false`；GodMode 分支 L1268–1273 失败时 WARN 并保留 CPU 倾斜。L175 目标 python PID 3616 失败，但后续 L209/220/231 等 Low 级别均成功——**这是目标句柄权限/进程保护问题，不是代码枚举 bug**，现有降级方向正确；缺陷只在进程退出与拒绝访问共用一条 WARN。

*电源计划*：
- **枚举代码没有 bug**。L1867 `powercfg /list` 正常；回执原件（`voice-retrain-power-balanced.json.result.txt`，282 B）里两条计划都列出来了。v3.log:193 "可用计划:" 后看似为空，是多行回执在日志首行只显示了第一行，续行在 L194–197。底账 §3 "枚举结果本身为空"的判读**不成立**。
- 实测当前机器 `/list` 只剩平衡（381b4222…）一条；高性能 GUID 8c5e7fda… 已不在列表（2026-11-19 只读枚举），而日志时点（11-16）两条都在、高性能为活动方案。
- L176 记录原计划 GUID 就是高性能 8c5e7fda，L177 又 `/setactive` 同一个 GUID 并 exit=1：聚焦路径 `Set-PowerPlanHigh`（L1151–1170）**没有"已是当前方案"守卫**；总线分支 L1871/1878 有这个守卫，两条路径行为不一致。
- exit=1 且 stderr 为空：可能是未提权、策略锁定、或目标方案已被删除。当前会话实测 `IsAdmin=True`；**日志时点内核进程是否提权未证实**（未取到该进程完整性级别），直接根因暂不能二选一。

**改法**：
1. 聚焦路径补"已是高性能则跳过"守卫，对齐总线分支。
2. 调 `/setactive` 前先用 `/list` 文本校验目标 GUID 存在；不存在则回执记一条跳过 note，不打 native exit=1 的 WARN。
3. 允许结论：本机高性能计划已被精简/删除时，**降级为不报错**——回执明确写"未切换：本机无此电源计划"，而不是 ERROR 染红界面；前端不得把这种 note 当成功绿标。
4. I/O 分支：调 `Set-IoPriority` 前先 `Get-Process -Id` 复查，退出走 INFO，拒绝访问才走 WARN（`Set-IoPriority` 目前只返回布尔、不带原因，这是最小改动边界；要带原因需扩返回值，列入后续）。

**改前**（L1164）：

```powershell
if (Invoke-Native -Exe "powercfg" -Args @('/setactive', $script:HighPerfGuid) -What "切换高性能电源计划") {
```

**改后**（守卫 + 存在性预校验）：

```powershell
$schemeList = (powercfg /list 2>$null | Out-String)
$curScheme  = powercfg /getactivescheme 2>$null | Out-String
if ($curScheme -match [regex]::Escape($script:HighPerfGuid)) {
    Write-Log "INFO" "当前已是高性能方案，跳过重复切换"
} elseif ($schemeList -notmatch [regex]::Escape($script:HighPerfGuid)) {
    Write-Log "INFO" "本机无高性能电源计划（OEM 精简或已删除），跳过电源优化"
} elseif (Invoke-Native -Exe "powercfg" -Args @('/setactive', $script:HighPerfGuid) -What "切换高性能电源计划") {
    Write-Log "INFO" "电源计划已切换为高性能"
} else {
    Write-Log "WARN" "切换高性能失败（exit=$LASTEXITCODE），仅保留 CPU 侧优化"
}
```

**验证**：`powercfg /list` 只读核对 GUID 存在性；分别在"高性能已在列表"和"已删除"两种状态下触发 focus，期望前者跳过重复切换、后者出跳过 note 且无 exit=1 WARN。
**回滚**：L1164 恢复单行 `Invoke-Native` 调用；新增的预校验块可整段摘除，不影响 `Restore-PowerPlan`。

## ⑦ 我可能错在哪

1. **PID 47596 跨周期复现的成因**：我判为"短命子进程被 OS 复用 PID"，但失败分支没记进程名，当时进程清单快照未留存；也可能是某个固定句柄或缓存名单在反复喂旧 PID。要坐实需要 `rules_state.json`/心跳落盘记录佐证，**未证实**。
2. **`/setactive` exit=1 的直接根因**：我只列了未提权、策略锁定、GUID 已删三种可能，没拿到日志时点内核进程完整性级别和 powercfg 实际报错文本；"重复切换同一 GUID"是代码事实（L176 vs L177），但 exit=1 直接原因**未坐实**。
