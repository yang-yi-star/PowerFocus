判断依据（代码/现场事实）：

3. **README 自我定位**："个人开发者维护的开源项目"。

### 2.2 0 star：规模问题还是传播问题？

**现有证据拆不开；偏向到达阶段问题，但价值未被证明是并列事实。**

- 偏向传播的依据：刚发版（v0.12.0，11-15），第二条视频尚在审核，没有证据表明有外部用户下载安装跑过；0 star 在"还没被看见"阶段是自然结果，不能反推没人要。

## ④ 做减法清单

### 4.1 砍掉 / 暂缓（3 项硬砍 + 1 项冻结）

**砍 1：KVRT 安全扫描链路（含每日自动扫描调度器）**
- 受损者：本机有杀毒需求的使用者（无证据存在）；已投入的下载/验签/扫描/报告链路。
- 损失：中等。README 已承诺该能力，暂缓需同步标注"可选、暂不主推"；三份副本 350.51 MB 清理另案，本轮不删代码。
- 可恢复：代码与版本库完整保留，重启只需启用入口。

**砍 2：云端 chat 兜底与云端模型路由对接**
- 受损者：想在面板对话云端模型的用户（0 证据）。损失小：`/api/chat` 当前未配置即 503，本就不可用。可恢复：凭据就绪后开放。

**砍 3：MCP 对外发布与新工具扩展**
- 受损者：未来通过 AI 客户端调用本机调度的外部开发者（0 证据）。已打包 zip 保留，本周不推广、不增工具。可恢复。

**冻结 4：新场景预设、新规则、三档加速扩展**——现有入口保留，本周不增规则、不调档位参数。

### 4.2 保留但降级（2 项）

**降级 1：MemGuard**——保留高位守护（warn 75% / critical 90% 不动），低水位段停止 1 秒一轮空转、降频；修复浮点直打 `357.09999999999997`（底账 §3 mem-guard 行 19）。受损面：极端压力下反应略延迟；阈值与修剪逻辑原样保留，可恢复。

**降级 2：场景 / 规则引擎 / boost**——入口与预设保留，本周不做规则编排可视化、不接新场景；无证据存在重度自定义用户。

### 4.3 本周必做（3 项）

1. **必现故障路径降级修复**：无电源计划 → 跳过并在面板说明，不再红字 ERROR；action 入口补非空校验；EcoQoS 设置前存活校验；I/O 权限不足给可读降级说明。
2. **MemGuard 空转治理 + 读数格式化**：低水位停转/降频，freed 数值规范化。
3. **失败原因前端可见化（最小反馈通道）**：配合架构师预留的 `request_id / error_code` 侧车字段（只写不读），前端先展示"成功 / 失败 / 失败原因"，为后续行为数据铺路。

## ⑤ 热感知调度值不值

### 5.1 现状：有高温读数，没有高温受害记录

- **有的证据**：LHM Tctl 峰值 94.0–96.5℃ 四个工作日重复出现，≥90℃ 记录 135/160/69/5 条（老钱 §3.2，A 级落盘）。
- **没有的证据**：
  1. 日志无降频、无推理变慢、无崩溃、无任务失败；无一条用户主观抱怨"烫/卡/慢"（底账 §7.6）。
  2. 口径未校准：空闲 6.1% 下 Tctl 仍 85.4℃，成因不明、无第二传感器；94℃ 与 ACPI 73℃ 是两个物理量，禁止并列（老钱 §3.4）。基线不紧张：内存空闲 50.5%、CPU 6.1%、GPU 54℃ / 8%。
- **94℃ 时用户遭遇了什么**：数据回答不了。掉帧、降频、变慢、没感觉，都无记录支撑——按协议这是"不知道"，不替用户补故事。

### 5.2 结论：本周不做热感知调度

RICE 0.15，全场最低。**本周只保留温度只读展示与落盘，不做任何按温度触发的调度决策**（自动降载、让路、限频一律不进本周范围）。

### 5.3 验证实验设计（痛点成立前不立项）

- **假设**：Tctl ≥90℃ 时段伴随可观测降频或吞吐下降；若只读数高、性能无变化，则痛点不成立。
- **通道固定**：CPU 用 LHM Tctl/Tdie，ACPI 仅参考，GPU 用 `nvidia-smi temperature.gpu`；先补第二传感器校准，未校准前阈值留 ≥10℃ 余量。
- **采集指标**（负载时段连续 ≥7 天）：温度（Tctl/CCDmax/GPU 温度功耗）；性能（CPU 当前频率 vs 基准、token/s 或响应时延）；稳定性（卡顿/崩溃计数、风扇转速）；主观（高温时段手动标注"卡/慢/无感觉"）。
- **判定**：高温段频率下调或吞吐下降且与温度相关、复现 ≥3 次 → 痛点成立，再设计策略；只读数高、性能无变化 → 只做提醒，不做自动调度。
- **次要指标**：风扇噪音、功耗；防止压温度牺牲推理速度。
- **时长**：7 天自然负载 + 1 次满载压测；样本不足不下结论。

## ⑥ 一周 MVP 范围 + 本周不做什么

### 6.1 这周做什么

必现故障降级修复与可读提示；MemGuard 空转治理与格式化；失败原因前端可见化、预留采集位；温度只读展示并标注通道；对外版本口径统一由产品拍板（health 1.00 / kernel v0.13 vs tag 0.12.0，底账 §2.3），工程落地不在本轮。

### 6.2 这周不做什么（5 项 + 理由）

1. **热感知调度闭环**——痛点未证实、温度未校准。
2. **KVRT 链路新投入**——每日调度器不常驻、不扩多引擎识别、不清理引擎副本（另案）。
3. **云端 chat / 云端路由对接、MCP 对外发布**——无外部使用证据。
4. **新场景、新规则、三档扩展、前端七页改版/新皮肤**——范围锁定，新增走变更流程，不"顺便加"。
5. **多引擎并行调度、消息队列/新总线抽象**——单机文件总线够用（架构师红线 §⑦），瓶颈未证实前不提前上抽象层。

## ⑦ 第二步触发条件

满足任一信号才立项评审；此前只做架构预留（沈工方案只写不读字段），不开发：

1. **外部用户**：≥3 名非本人使用者完成安装，各跑通 ≥1 次调度动作。
2. **行为留存**：埋点显示核心动作周触发频次稳定，次周仍有使用（阈值待基线后定）。
3. **痛点证实**：§5.3 实验证明高温与降频/吞吐下降相关且复现 ≥3 次。
4. **外部反馈**：issue/评论/社群集中指向同一痛点 ≥3 条，且与行为数据交叉验证一致。

## ⑧ 用户视角验收标准（5 条，可测）

1. **托盘不出错**：启动后 `/api/health` 返回 `ready=true`；连续 7 天无认证失败红条。测法：重启一次，连下 10 条命令，回执无认证类 ERROR。
2. **点了有用，失败说人话**：对运行中目标进程让路/提优先级，回读校验通过；缺权限/无计划场景展示可读原因，不再出现"未知 action:"空信息。测法：3 类典型场景各人工操作 1 次。
3. **环境性失败不再报错**：无电源计划时切换路径结果为"已跳过 + 原因"，而非红字 ERROR。测法：本机触发一次电源路径，核对回执与文案。
4. **温度看得懂**：标注通道（CPU Tctl / GPU / 平台热区），峰值可查；94℃ 与 73℃ 不并列对比。测法：打开温度页核对来源标签。
5. **内存守护不空转刷屏**：低水位不再 1 秒一条 `trimmed=0`；高位仍能实际回收（基线：162 次空转 / 2 次修剪，老钱 §5.2）。测法：空闲观察 + 一次内存压测，核对条数与回收量。

## ⑨ 对其他岗位的质疑

1. **对架构师/前端**：预留了 `error_code`，但前端差异化展示契约未定；第二步落地前不定"什么错误码对应什么提示"，字段会白加。请先给错误展示口径。
2. **对数据分析师/DevOps**：校准完成前，对外文案、视频脚本不得出现"过热""降频保护"；实验的频率基准、token/s 采样窗口需先定，否则结论不可比。
3. **对开发**：六类故障证据等级不同——电源计划、action 封装属必现；认证失败仅单一时点、改名后即通过。不要当稳定缺陷直接改，先复现拿到 ≥2 个时点样本再定性。
