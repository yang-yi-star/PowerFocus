## ③ 可用性缺陷清单（10 条，均带代码位置）

### D-01 「终止进程」工具栏按钮是死按钮
- **位置**：`index.html` L146 `data-kill="1"` 按钮；`app.js` L887 只绑定 `.ops [data-cmd]`，全文无 `[data-kill]` 监听；终止逻辑只挂在进程行双击上（L914–920）。
- **遭遇**：选中进程点「终止进程」，无确认框、无 toast、无反应；用户重复点击，以为卡死。
- **原因**：HTML 留了钩子，JS 绑定漏接；危险动作唯一入口是无提示的双击手势，接近不可发现。
- **影响**：高。直接命中底账"点了没反应"隐患。
- **修法**：补 `[data-kill]` 绑定，复用 L917 确认框与 `kill_process`。纯前端 0.5–1h，不动后端。

### D-02 后端报错原文直抛用户
- **位置**：`runCommand` L389–390 把 `r.text` 抛成 Error；`guard` L401–404 直送 toast；`api()` L146–149 取 `j.detail`；聊天 L494–497、L516、L527 同构。后端文案如「action 不在白名单: %s」「messages 必须是 <=50 条…」（server.py L963、L1013）原样上行。
- **底账旁证**：§3 L328/330「ERROR: 未知 action:」（action 为空）；L192–193「切平衡失败…可用计划:」（枚举为空）；L422–423 令牌失败原文。
- **遭遇**：看到空尾巴的"未知 action:"、令牌名、英文枚举，看不懂也不知道下一步。
- **原因**：错误文案是开发者排障语言，前端没有"内部错误→用户语言"映射层。
- **影响**：高。不可读的报错会诱发乱点、重复提交。
- **修法**：前端建归类表（令牌失效→「授权已失效，请重启应用」；计划缺失→「本机没有该电源方案，已跳过」；不支持→「这条指令没听懂，换个说法」），原文折叠进日志视图。纯前端 2–3h；后端返回结构化错误码属加分项。

### D-03 温度通道前端完全缺席
- **位置**：`app.js` Grep `temp|温度|gpu|GPU` **0 命中**；HTML 无温度元素。后端已具备：`/api/temp`（server.py L896–906，落盘 cpu.tctl/ccd_max、gpu.core/mem_junction）、快照内 `d.gpu`（L927，`gpu_thermal` L645–679）。
- **遭遇**：风扇狂转、机器发烫时界面无任何温度线索，85℃ 是好是坏无从判断。
- **原因**：采集落盘在前，展示层没接；顶栏只有 CPU% 与内存%，无温度位。
- **影响**：高。调度工具缺主仪表。
- **修法**：见 §④；前端 4–6h；后端接口已存在，不需新接口；阈值口径由数据分析师冻结。

### D-04 异步操作无忙碌态，可重复点击
- **位置**：进程按钮 L887–903；快捷指令 L944–947；路由启停 L949–964；聊天发送 L976 / `sendChat` L478–530，均不 disabled、不改文案。对照：自检 L583/L605、组件 L725/L737/L754/L764 有正确 disable 模式。
- **遭遇**：内核慢（`start_router` 预算 180s，L386–387）时连点两次 → 两条命令进总线；聊天可并发多条流，回复错乱。
- **原因**：忙碌态只在个别按钮手工实现，缺统一"点击锁定、完事恢复"模式。
- **影响**：中高。重复命令可能重复调优先级、重复下载。
- **修法**：抽 `withBusy(button, promise)`：点击后 disabled +「执行中…」，`finally` 恢复。纯前端 2h。

### D-05 轮询失败后静默停摆，旧数据无过期标识
- **位置**：`schedulePoll` L856–867：`pollErrors >= 5` 后直接 `return`，定时器仍跑但不取数；仅第 1 次失败发 toast（L865）；`renderSnapshot` 未读 health 的 `ready`/`frozen`（底账 §1 有此二字段，前端未消费）。
- **遭遇**：内核掉线后界面停留旧值，状态点仍显"在线"，分不清实时还是冻结。
- **原因**：缺数据时效时间戳与"最后更新于 xx:xx"表达；到阈值后永久放弃而非降频重试。
- **影响**：高。正是"内核活着/死了能否看出"的核心诉求。
- **修法**：连续失败 N 次后判定条与内核胶囊显示「数据已过期 · 最后更新 xx:xx」+ 手动重连；阈值后降频重试。前端 2h；后端补时间戳可选。

### D-06 路由状态靠正则猜自由文本
- **位置**：`renderRouter` L456，用 `/running|true|已运行|运行中.../` 匹配后端自由文本。
- **遭遇**：后端换措辞（started/active）后，实际在跑却亮"未启动"，反之误判；用户据此重复启停。
- **原因**：状态语义用文本模式匹配而非结构化布尔，脆弱不可测。
- **影响**：中。误判可致重复启动路由、抢占显存。
- **修法**：后端返回 `running: bool`，前端只认布尔。后端 1h + 前端 0.5h；纯前端正则修不掉根因。

### D-07 进程状态列直出 Windows 优先级枚举
- **位置**：`renderProcessTable` L342，`p.priority` 原样入表（BelowNormal/AboveNormal/Normal/Idle）。
- **遭遇**：看不懂 BelowNormal；点完"聚焦·高"也认不出变没变。
- **原因**：内部枚举名直接进用户界面，缺中文映射层。
- **影响**：中。状态不可辨 + 术语外露。
- **修法**：映射「高于正常/正常/低于正常/空闲」，未知值保留原文标「未知」。前端 0.5h。

### D-08 指令解析回退成命令 JSON
- **位置**：`cmd-run` L929–931，无 `_explain` 时 `JSON.stringify(r.command)`；确认框 L931 同一回退。
- **遭遇**：用户看到 `{"action":"set_priority","mode":"godmode"}` 结构。
- **原因**：缺人话兜底，直接序列化命令对象。
- **影响**：中低。开发者视角残留，削弱信任。
- **修法**：无 `_explain` 时用字段拼人话；JSON 收进日志展开区。前端 1h；后端补 `_explain` 覆盖率更佳。

### D-09 空态与审计列表泄露内部字段/文件名
- **位置**：场景空态 L416「scenes.json 中没有场景」；审计 `renderAudit` L572–577 把事件元字段拼成 `key=value` 平铺。
- **遭遇**：见 `scenes.json` 以为文件损坏；审计页见 `event=auth_fail token_hash=...` 堆叠，无中文、无级别配色。
- **原因**：空态与事件渲染都站开发者视角，缺转译与折叠。
- **影响**：低–中。不阻断操作，但增加困惑。
- **修法**：空态改「暂无可用场景」；事件类型译中文 + 级别配色，元字段二级展开。前端 1.5h。

### D-10 聊天无空态/无输入中占位；前端日志只含本会话
- **位置**：`chat-list` L192 初始空且无引导；`sendChat` L486 气泡起手空串，等待期间无"正在输入"；`chatHistory` L18 纯内存。日志 `logLine` L123–127 只收前端事件，`renderLogs` L847–851；底账 §3 的 EcoQoS/令牌/切平衡失败、浮点 `357.0999…` 都只在文件日志。
- **遭遇**：首屏一片空白不知问什么；慢回复看空气泡像卡死；出问题翻界面日志找不到原因。
- **原因**：空态/加载态未设计；前后端日志链路未接通。
- **影响**：中。引导弱、排障路径长。
- **修法**：空态给 2–3 条示例；发送中加省略占位；日志先注明"仅记录本界面操作"，接内核事件流列后续。前端 1.5h；日志接入后端 2h。

## ④ 温度与算力可视化方案（本轮最关键交付）

### 4.1 原则

- **不堆仪表盘**：不做半圆表盘/伪精确指针；每通道一行"状态点 + 中文档位 + 整数温度 + 来源/时点小字"。
- **不假精确**：℃ 取整；缓存旧于采样间隔标注"x 秒前"；字段缺失/N/A/超时走不可信降级，不猜数。
- **通道不混用**（依数据分析师 06 号文 §3.4）：CPU 用 LHM Tctl/Tdie（`cpu.tctl`/`cpu.ccd_max`）；GPU 用 `nvidia-smi temperature.gpu`；ACPI 热区仅平台参考，不上主视图、不参与分级。两通道禁止互相替代、取平均、跨通道比阈值。
- **留余量**：第二传感器校准前阈值预留 ≥10℃；空闲 85.4℃ 成因未验证，不得直接判"过热"。

### 4.2 三档 + 降级（档位结构先行，数字待冻结）

| 档位 | 视觉 | 文案 | 触发原则 |
|---|---|---|---|
| 正常 | 绿点 success | 「温度正常」 | 偏低区间，无告警 |
| 偏高 | 琥珀 warning | 「温度偏高，建议关掉后台占用」 | 进入余量带，距保护线 ≥10℃；不刷屏不强弹窗 |
| 过热 | 红点 danger + 判定条建议 | 「温度过高，建议停止重负载并散热」 | 达/近保护线；数值阈值待校准后冻结 |
| 暂不可用 | 灰点 ghost | 「温度暂不可用」+ 小字原因 | 传感器缺失/N/A/超时/缓存过旧/来源不明；不套色、不显示猜测值 |

### 4.3 布局草图（总览新增「温度状况」面板，置 TOP8 旁 split 区）

```
┌─ 温度状况 ──────────────────────────────────────────┐
│  CPU 封装   ● 正常   71℃   Tctl · 5 秒前采样        │
│  GPU 核心   ● 偏高   63℃   利用率 18% · 显存 2.5/8GB │
│  ── 次级（折叠）──────────────────────────────────  │
│  GPU 显存结温  --  ·  ACPI 平台热区 73℃（仅参考）   │
└─────────────────────────────────────────────────────┘
```

- CPU 行走 `/api/temp`；GPU 行走快照 `d.gpu`（字段见 L629–642）。
- 不可信降级：无 NVIDIA 设备 → GPU 行「未检测到独显」；LHM 无数据 → CPU 行独立标注，**不拿 ACPI 顶替 CPU 行**；后端 `error`（L665/671/673/675）收进 tooltip 小字。
- **落地手段**：复用现有状态色双轨、`.dot`、`.kv`、`.verdict`；不引图表库；`style.css` 增补少量 `.temp-row` 规则，容器沿用 `.panel`/`.split`。降频原因 `throttle_reasons` 先收次级展开。

## ⑤ 做减法（3 项 + 损失）

1. **独立「日志」视图降为二级入口**：现日志仅前端本会话 200 条内存事件（D-10），收起为判定条旁"查看事件"。损失：少一个独立翻页，排障多点一次；现有内容本就不含内核告警，不丢关键能力。
2. **安全基线运维细节默认折叠**：令牌指纹/路径、接口地图、请求体上限、响应头（L550–558）收进「高级安全信息」。损失：排查配置多一次展开，日常用户不需要上墙。
3. **设置页「运行信息」并入自检页**：指纹、内核/程序目录、密钥来源（L782–787）与组件自检同域。损失：设置页少一块速查；目录信息集中一处反而更一致。
4.（备选）顶栏「云端」胶囊与模型视图目标选择重复，可只留内核/路由两枚；损失：一眼分辨云/本地的便利，由模型视图选择器承担。

## ⑦ 长期迭代来源（3 条，先不加埋点）

1. **四态截图走查 + 文案审查清单**：每轮发版前按「空态/加载态/错误态/极端数据（超长名、缺字段、零进程）」逐视图截图归档对比；错误文案逐条过清单：是否含 action 名、JSON、工程文件名、英文枚举、空尾巴冒号。零代码，固化进流程。
2. **错误文案人工归集**：每周把 `clientLog` 200 条与文件日志里的 err toast、`r.text` 翻一遍，归类回填 D-02 映射表；先不做埋点，靠现有日志周审。
3. **微型可用性测试**：每次改动后找非开发人员完成三任务——找前台进程、切高性能、发一条对话，记录卡点与时长；失败点回流缺陷清单。热力/停留埋点列为后续可选。

## ⑧ 对其他岗位的质疑

1. **问后端/开发**：`/api/snapshot` 为何不带采样时间戳、不透传 health 的 `ready`/`frozen`？前端无法区分实时与旧缓存，D-05 只能靠失败次数猜；快照是否应附 `last_updated` 与冻结标志？
2. **问后端**：路由状态能否直接给结构化 `running` 布尔？L456 正则在后端措辞调整时必然漏判，前端修不掉根因。
3. **问数据分析师**：校准前 CPU/GPU 档位边界各留多少余量？ACPI 是否确定只进次级参考、不进分级？空闲 85.4℃ 在文案上如何表达才不误导成"过热"？
4. **问产品**：聊天历史是否持久化（现纯内存刷新即丢）？日志视图定位用户排障还是开发者排障——决定 D-10 接不接内核事件流。
