仓库有 **3084 个文件 / 523.4 MB**，但真正的核心代码只有 **约 4 MB**（150 个 `.ps1` 共 2.1 MB、90 个 `.py` 共 1.9 MB），占总量 **0.8%**。剩下 99% 是引擎二进制、exe 备份、视频素材和历史副本。

## 3. 真实结构：一个内核，三层外壳

```
┌─ 第 4 层  MCP 入口 ─ mcp/powerfocus_mcp/server.py（550 行）
│    14 个工具，stdio JSON-RPC，零第三方依赖，默认只读 10 个
│    ↓ 全部通过 HTTP，复用 X-PF-Token
├─ 第 3 层  HTTP 服务 ─ product/v1.00/app/server.py（52.2 KB / 22 条路由）
│    鉴权 / 限流 / CSP / 命令总线 / 安全态势 / 组件引导
│    ↓ 写 commands/in 文件，轮询 commands/done
├─ 第 2 层  内核 ─ versions/v0.09/电脑算力调度中心_v0.09.ps1（1968 行 / 59 函数）
│    + rules-engine.ps1（341 行）
│    + lib/*.ps1（app-purger / mem-guard / model-registry / rollback / geek-bridge / clean-recyclebin）
│    ↓ 进程优先级 / IO 优先级 / 内存回收 / 电源计划 / 场景 / 看门狗
└─ 第 1 层  界面 ─ product/v1.00/app/web/（index.html 16.3KB + app.js 44.2KB + css 33KB）
```

**数据流**：`app.js` → HTTP → `server.py` → 文件总线 → 内核 `.ps1` → Windows API

**这层结构的实质**：内核才是干活的那个（3572 行本机资源治理），Python 侧是采集 + 协议适配 + 呈现。

## 6. 与用户定位的差距对照

| 用户定位 | 代码实况 | 差距 |
|---|---|---|
| 整机聚合成**一个总算力池** | 内核按进程逐个调优先级，没有「池容量/余量/水位」概念 | **缺池级抽象**：无总算力额度、无水位、无分配账本 |
| 调度单位是**算力**，不是进程 | 59 函数全部以 PID 为单位 | **缺算力度量**：无 tokens/s、无 FLOPs、无显存页作为单位 |
| **统一内存架构**保证本地模型优先 | `统一内存模式.ps1` 存在但零引用 | **能力在，入口不在**（见 5.3） |
| 有**系统级高权限** | `build\app.manifest` 声明 `requestedExecutionLevel level="asInvoker" uiAccess="false"` | **需澄清**：`asInvoker` 只表示「不主动请求提权」，不等于「权限低」——以管理员身份启动时进程仍拥有完整管理员权限。真正的限制是：不主动提权时，PPL 进程操作会被拒、部分系统 API 不可用 |
| 有**反攻/入侵/网络攻防**能力 | `security.py` 是防护（鉴权/限流/CSP/DPAPI），`engine_adapters` 是查杀；**无主动攻防** | **缺一块**：无入侵检测、无网络侧探测、无攻击面评估 |
| **内置 RAG** | 零实现。`bge-m3:latest`（1.2 GB）+ `nomic-embed-text`（274 MB）模型在本机装着，但没有代码用 | **有模型，无引擎** |
| 与**温度系统高度融合** | **零实现（已实测）**：v0.09 主脚本全文仅 1 处 `nvidia-smi`（行 1555，查 `--query-gpu=memory.free` 显存空闲，**不是温度**）；`rules-engine.ps1` 温度类关键词 0 命中；`server.py` 温度/NVML 0 命中。NVML 的 `nvmlDeviceGetMarginTemperature` / `GetCurrentClocksEventReasons` 接口确认可用，但无一行业务代码调用 | **有路径，无代码** |
| 优先给本地模型最大空间 + 把搭配应用一起支持 | `Get-ProcessValueRank` 有五档分级，`task` 档保护"后台干活"的进程 | **部分具备**：能保护，但没有"给模型让路"的主动腾挪 |
| **只做 Windows** | `app_paths.py` 有非 Windows 分支，`server.py` 有跨平台痕迹 | **基本符合**，少量跨平台残留 |
| **单版本迭代**（废弃 versions/ 多版本） | 6 个版本目录 + `current.json` 指针 + `new-version.ps1` | **未执行** |
| 危险动作由 AI 直接向顾客说明 | MCP `pf_run_command` 需要 nonce 二次确认 | **方向相反**：现在是强制确认，用户要的是说明即可 |

## 7. 该做的第一件事

**不是重构，是接线。**

三层外壳已经完工，内核 59 函数在跑，KVRT 真扫通过，bootstrap 真装过 Node。仓库不缺能力，缺的是**把已有的能力接到该接的地方**：

1. `统一内存模式.ps1` → 接进内核，加 3 个函数：`Start-UnifiedMemoryAsPool` / `Get-PoolStatus` / `Stop-UnifiedMemoryPool`
2. 加一条 `/api/pool` 路由 + 一个 `pf_pool` MCP 工具
3. 加一条 `/api/security/scan` 路由 + 一个 `pf_security_scan` MCP 工具（复用已跑通的 `kvrt_bundle.run_scan`）
4. 温度：`nvmlDeviceGetMarginTemperature` + `GetCurrentClocksEventReasons` 接进快照，进 `/api/snapshot`
5. RAG：`bge-m3` 已在 Ollama，接一条 `/api/rag` 即可

这五件事全部是**接线**，不是发明。做完再谈"重排"。

在接线之前，先处理一件会污染所有测量的东西：

- **72 个无 BOM 的 .ps1**（编码债，已害过 `build.ps1` 一次）

### 8.5 统一内存模式的真实形态 —— 已读清，**尚未接线**

`统一内存模式.ps1`（854 行 / 14 个函数）的真实定位：**给 llama.cpp 用的启动器**，不是通用的算力池内核。

| 函数 | 干什么 |
|---|---|
| `Get-GpuMemoryInfo` | 读显存 |
| `Get-SystemMemoryInfo` | 读内存 |
| `Get-GgufLayerCount` | 从 GGUF 头解析总层数 |
| **`Calculate-OptimalLayerSplit`** | **核心：按显存算 GPU/CPU 分层（这才是可复用的算力池容量模型）** |
| `Build-LlamaServerArgs` | 拼 `llama-server` 参数 |
| `Start-UnifiedMemoryMode` | 启 `llama-server` |
| `Monitor-WeightDistribution` | 监控权重分布 |
| `Show-MemoryStatus` / `Stop-UnifiedMemoryMode` | 展示 / 停止 |

关键的脚本级常量（决定了「能跑多大模型」）：

```
CudaReservedMB   = 512      # cuDNN/cuBLAS 工作区
ComputeReserveMB = 1024     # 计算缓冲 + KV 预留
MaxGpuLayersSafe = 20       # RTX 5060 8GB 实测 -ngl 20 约 7.5GB，21 层以上 OOM
CtxSize          = 65536
ModelPath        = E:\Model_Zone\Qwen3.8-27B-UD-Q4_K_M\...
LlamaServerPath  = "E:\Program Files\llama.cpp\bin\llama-server.exe"
```

**接线判断**：可复用的是 `Calculate-OptimalLayerSplit` + `Get-GpuMemoryInfo` + `Get-SystemMemoryInfo` 这一组**容量计算**，它回答「这台机器能装多少层进显存、多少留给内存」——这正是「整机一个算力池」的可计算形式。

**不该接**的是 `Start-UnifiedMemoryMode`：那是启 `llama-server` 的，而 v0.09 内核是进程/算力调度器，不是推理服务管理器。**接错了会把产品变成 llama.cpp 的启动壳**。
