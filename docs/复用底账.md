## 一、判断先行

这个应用现在的问题不是能力不足，是**四种分裂**：

| # | 分裂 | 具体表现 |
|---|---|---|
| 1 | 形态分裂 | 脚本（`电脑算力调度中心.ps1`）+ Python 后端（`app/server.py`）+ 打包 exe（`product/v1.00`）+ Web UI（`app/web`）+ MCP（`mcp/powerfocus_mcp`），五套入口并存 |
| 2 | 版本分裂 | `versions/v0.05`–`v0.10` 六个目录 + `current.json` + 根目录转发壳，用户已定"单版本迭代" |
| 3 | 账本分裂 | CPU 一套口径、内存一套口径、显存一套口径、网络一套口径，没有统一的"算力"指标 |
| 4 | 权限分裂 | 脚本跑在 pwsh、服务跑在 python、MCP 跑在 stdio、GUI 跑在 exe，四者权限边界与生命周期不一致 |

一句话：**零件齐，装配散。** 重构主线不是加功能，是把这四道裂缝合上。

## 三、Windows 官方现成的（不许重造）

### 3.1 CPU 与调度

| 能力 | API | 说明 |
|---|---|---|
| 按权重分 CPU | `JobObjectCpuRateControlInformation` + `WEIGHT_BASED`（Weight 1–9） | 相对权重，非绝对 |
| 按硬顶分 CPU | 同上 + `HARD_CAP`（CpuRate 千分比） | 到点即停，下个间隔才恢复 |
| **保底 + 上限** | 同上 + `MIN_MAX_RATE`（MinRate / MaxRate） | **全系统 MinRate 之和 ≤ 10000，零和，必须做取舍** |
| 优先但不饿死 | **MMCSS**（`AvSetMmThreadCharacteristics`） | 默认 `SystemResponsiveness=20`，即永远留 20% 给低优先级 |
| 后台节能 | EcoQoS（`SetThreadInformation` + `THREAD_POWER_THROTTLING_EXECUTION_SPEED`） | 只用于后台，**不可用于前台/性能关键推理** |
| 内存压力回收顺序 | `MEMORY_PRIORITY_INFORMATION`（`ProcessMemoryPriority` / `ThreadMemoryPriority`） | **不减少实际占用，只影响 trim 先后** |
| 感知系统内存压力 | `CreateMemoryResourceNotification` | 低内存通知到达后再决定卸谁 |
| 作业级内存/IO 上限 | `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`（`JobMemoryLimit`、`ProcessMemoryLimit`、IO 字节上限） | 硬限，超了即失败 |
| 作业级 UI 限制 | `JOB_OBJECT_UILIMIT_*`（剪贴板、桌面切换、ExitWindows 等） | 沙箱配套 |
| 真沙箱 | `Experimental_CreateProcessInSandbox` + `app_container` | 内核级隔离、网络隔离、文件系统隔离；**无 AppContainer 时其它限制字段全部无效** |

**结论：CPU 侧的"给模型最大、给别人最小"，Windows 原生就有 `MIN_MAX_RATE`，不需要自己写调度器。**

### 3.2 显存与 GPU 台账

| 用途 | 来源 | 关键坑 |
|---|---|---|
| 总显存 | `DXGI_ADAPTER_DESC1.DedicatedVideoMemory` | `Win32_VideoController.AdapterRAM` 是 32 位，>4GB 一律报 ~4GB，**不可用** |
| 可用预算 / 当前占用 | `IDXGIAdapter3::QueryVideoMemoryInfo`（`LOCAL` / `NON_LOCAL`） | Windows 允许 GPU 借用最多一半物理内存作 Shared，8GB 卡 + 32GB 内存会显示 24GB，**只有 8GB 是真 VRAM** |
| 进程级显存 | 性能计数器 `\GPU Process Memory(*)\Dedicated Usage`（实例名 `pid_XXXX`） | **WDDM 下 `nvidia-smi` 取不到进程级用量，返回 N/A**，这是唯一可行路径 |
| 进程级 GPU 利用率 | `\GPU Engine(pid_XXXX_engtype_3D_*)\Utilization Percentage` | 实例名由 OS/驱动定义，**必须枚举（`PdhEnumObjectItems`），不能拼** |
| 温度阈值 | `nvmlDeviceGetTemperatureThreshold`（`SHUTDOWN` / `SLOWDOWN` / `MEM_MAX` / `GPU_MAX`） | 硬件自己给红线，不用猜 |
| 离降速余量 | `nvmlDeviceGetMarginTemperature`（distance to nearest slowdown threshold） | **这才是调度该用的"温度"指标** |
| 是否正在降频及原因 | `nvmlDeviceGetCurrentClocksEventReasons`（热降速 / 功耗墙 / 板限 / 可靠性） | 官方位掩码 |
| 降频累计时长 | `nvmlDeviceGetViolationStatus` | 热降速部分暂不支持 |
| 功耗与功耗墙 | `nvmlDeviceGetPowerUsage` / `nvmlDeviceGetEnforcedPowerLimit` | 后者是所有限制器叠加后的实际值 |

**结论：GPU 全部走 NVML + DXGI，零内核驱动，不与卡巴斯基冲突。CPU 温度无官方 API，改判"是否降频"（`CallNtPowerInformation(ProcessorInformation)` 取实时频率对比基频）。**

### 3.3 观测与形态

| 用途 | 方案 |
|---|---|
| 计数器采集 | PDH（`PdhEnumObjectItems` → `PdhAddCounter` → `PdhCollectQueryData`）；OneCore 应用改用 PerfLib V2 |
| 高层遥测 | ETW；结构化导出走 OpenTelemetry（MCP 2026 版已把 Logging 弃用、指向 stderr / OTel） |
| 常驻形态 | Windows Service（策略引擎，无 GUI 也能跑）+ 托盘（仪表盘）+ 命名管道/回环 IPC |
| 单实例 | 互斥体 + 命名管道抢占 |

## 四、实测事实（决定优先级，来自自有报告）

| 场景 | t/s | 相对基线 | 出处 |
|---|---|---|---|
| 不调动（24 个 node 占满 27 核，整机 94%） | 1.20 | — | 算力调度对比报告 |
| 温和聚焦（同上竞争环境） | 1.32 | **+10.0%** | 同上 |
| 激进聚焦（同上，降级 177 个进程） | 1.31 | **+9.2%** | 同上 |
| 统一内存形态（无竞争、热缓存、`-ngl 20 -fa off -c 8192`） | 2.81（均值）/ 3.43（校准轮） | **+134%（对比 1.20）** | 统一内存实测报告 |

三条硬结论：

1. **调度的真实收益是 10%，不是十倍。** 任何对外表述都必须用这个数。
2. **激进档降级 177 个进程，收益为 0**（1.31 vs 1.32，波动范围内）。过度压制没有边际收益，只有风险。
3. **形态的价值远大于调度**：MMAP 共享同一份权重 + 分层计算，值 +134%；调度值 +10%。

**最大未知（第一优先级实验）：** 两者从未叠加测过。统一内存形态 + 温和聚焦一起开，是 2.81 还是更高？这个数决定产品主线到底是"调度器"还是"形态引擎"。

补充口径（诚实标注）：`2.81` 与 `1.20` 的差距主要来自"无竞争 + 热缓存"，不能全部归功于统一内存形态本身。二者不是同一条件的可比实验，**必须重做一次同条件 A/B**。

| # | 缺口 | 为什么必须有 | 复用基础 |
|---|---|---|---|

## 六、重排后的结构（建议）

```
PowerFocus/
  kernel/                      # 内核：无 GUI 也能跑
    probe/       探测层        # CPU / 内存 / 显存 / 网络 / 降频事实
    ledger/      账本层        # 统一算力指标 + 分项 + 瓶颈标签
    budget/      预算层        # 权重 + KV + 工作区 + 桌面 + 余量
    policy/      策略层        # 白名单 / 工作集识别 / MIN_MAX_RATE 分配
    guard/       守护层        # 看门狗 / 自愈 / 回滚
  service/                     # Windows Service 宿主
  mcp/                         # MCP Server（产品主入口，AI 调这里）
  console/                     # 人的仪表盘（只读优先，写操作二次确认）
  quarantine/                  # 隔离区 + 准入流水线（卡巴斯基在此环节）
  tests/                       # 同条件 A/B 验收
  docs/
```

分层原则：**探测层只报告事实，账本层只算数，预算层只提方案，策略层才动资源，守护层兜底回滚。** 每层单独可测，出错能定位到层，不用整机重启。

## 八、勘正与补充（2026-11-14 实测，推翻本文两处判断）

本文初稿是在只读了根目录的情况下写的，读到 `versions\v0.09` 与 `versions\v0.10` 后，以下两处**必须改正**：

### 勘正 1：准入与隔离不是缺口

初稿第五节把"卡巴斯基那一环"列为待造缺口。**错了。**

`versions\v0.10` 里已经有真实跑通的链路（README 自述，2026-11-12 实测）：

| 文件 | 真实状态 |
|---|---|
| `kvrt_bundle.py`（37.4KB） | 官方源下载 → WinVerifyTrust 验签 → 真实扫描 → 官方报告解析 → 应用内每日调度 |
| `security_scan.py`（19.3KB） | 引擎识别（WMI SecurityCenter2）、适配器注册表 |
| `engine_adapters.py`（43.5KB） | 多引擎适配层，识别本机已装安全软件 |
| 实测记录 | 2026-11-12 13:12 真扫 **6,943 个对象**，Detected=0 / Found=0，退出码 0 |

已踩过的坑（写进 README，不用再踩）：KVRT 是 2020 内核，`-customonly` 不识别会弹帮助窗口挂起 24 分钟；`-d <path>` 是空格分隔两个参数；报告是 XOR 0xEF 编码的 XML；威胁数必须取官方字段。

真正的缺口不是"造能力"，是**接线**：`versions\current.json` 仍指向 v0.09，`product\v1.00` 的 exe 组件自检里，`kaspersky_free` 只是"待办项（vendor_installer）"。**能力躺在 dev 版本里，生产没接上。**

### 勘正 2：调度不是"无脑压进程"

初稿与之前的口头评价都把它当成"优先级压制器"。**错了。** `v0.09` 主脚本（103.9KB）里有一整套价值分级：

`Get-ProcessValueRank` 把每个进程判成五档，据此差别处置：

| 档位 | 处置 | 依据 |
|---|---|---|
| `protect` | 不动 | 系统关键进程、白名单 |
| `active` | 不动 | **用户正在交互（前台进程树）** |
| `task` | 不动 | **后台在干活：下载 / 训练 / 渲染 / 编译** |
| `semi` | 压低到 BelowNormal / Idle | 有占用但无明确用途 |
| `junk` | 启动 >120s 且无窗口+无输入+CPU 空闲+无 TCP 连接 → 杀；刚启动的只压不杀 | 真垃圾 |

判定输入不只看名字，还看：前台 PID、DeepSeek 进程树（`DsTree`）、授权应用名单、`BusySet`（CPU 活跃度）、`TcpSet`（网络连接）、父子关系、窗口句柄。

另有：目标提 AboveNormal / High / RealTime 三档、`PriorityBoostEnabled`、**IO 优先级（`NtSetInformationProcess` ProcessIoPriority）**、电源计划切高性能、watchdog 按期望优先级守护、`Stop-Focus` 还原原值（v1 遗留"永久 High"已修）。

**结论：这是一台有价值观的调度器，不是压制器。** 之前拿"优先级教科书"来批它，批错了对象。

### 补充：exe 启动竞态（真实缺陷，未修）

`desktop.log` 2026-11-14 06:29:12 记录「内核启动超时（10 秒内未见心跳）」，界面因红条"内核未响应"、CPU 0.0%、内存 NaN。

后续 08:22 / 08:27 / 08:29 / 08:30 / 09:07 / 09:08 / 10:05 / 10:26 八次启动全部正常（"内核已在线"）。**这是启动竞态，不是稳定故障**：exe 拉起 pwsh 内核后固定等 10 秒心跳，而 27B 级机器在冷启动或磁盘繁忙时，pwsh 加载 104KB 内核 + 初始化规则引擎可能超过 10 秒。

修法：把固定 10 秒等待改成**指数退避重试**（10s → 20s → 40s，总上限 90s），并在等待窗口内每 2 秒读一次心跳文件，读到即放行。这比单纯延长超时更稳，因为正常机器不会被拖慢。

有 BOM 的仅 8 个：`diag-engine.ps1`、`test-functional.ps1`、`tests\run-tests.ps1`、`tools\dev-check.ps1`、`tools\disable-runtime-tools.ps1`、`tools\env.ps1`、`build\build.ps1`（本轮已修）、`Test-ComputeMatrix.ps1`（本轮新建）。

**风险说明（不夸大）**：v0.09 内核由 exe 以 `pwsh -File` 拉起时能正常运行（心跳 rules_running=true / cmd_bus=true），说明该路径下编码解析未必走 ANSI；但本轮实测已证明**在当前交互会话里执行无 BOM 的 build.ps1 会被按 GBK 读**。同一台机器出现两种行为，说明编码依赖调用路径，属不稳定因素。

**建议**：统一给全部 .ps1 加 UTF-8 BOM（幂等、只改编码不改内容），一次修完根除。不要一个个碰运气。

**2. API 中文乱码**

`http://127.0.0.1:18080/api/health` 返回：
```
{"name":"鐢佃剳绠楀姏璋冨害涓績", ...}
```
"电脑算力调度中心" 被 GBK/UTF-8 错位编码。看界面正常，说明问题在 JSON 响应的编码声明或序列化参数上（`ensure_ascii` / `charset`），需在 `server.py` 的响应构造处定位。

**3. ~~双内核并存~~ ← 本判断已被实测推翻，此处保留以记录错误**

初判为「两个内核同时运行、互相争抢」。查命令行后为误判：

| PID | 命令行（实测） | 真实身份 |
|---|---|---|
| 59996 | `pwsh -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File "E:\PowerFocus\versions\v0.09\lib\mem-guard.ps1" -IntervalMs 1000 -CacheMs 5000` | **内存守护子模块** |
| 61404 | `pwsh -NoProfile -ExecutionPolicy Bypass -File E:\PowerFocus\versions\v0.09\电脑算力调度中心_v0.09.ps1` | 主内核 |

**结论：一个内核 + 它的守护子进程，架构正常，无缺陷。** 我此前把它当成「实例锁失效」是错误的——判断依据只是「看到两个同名 pwsh 进程」，没有先查命令行。这正是「以瞎猜接口为耻」反过来的那种错误：看到形状就下结论。

**4. 矩阵实验环境不满足（阻塞）**

| 项 | 需要 | 当前 | 结论 |
|---|---|---|---|
| 27B 纯 CPU 档内存 | 17.3 GB | 5.2 GB 可用 | 不可跑，会重度 swap |
| 27B 分层档显存 | 约 6.1 GB | 3.7 GB 可用 | 不可跑，必 OOM |

显存被谁占了（性能计数器实测）：`dwm` 1584MB、`msedge` 700MB、`DoubaoWork` 813MB、`JianyingPro` 395MB、`QQ` 512MB、其余若干，合计约 4.9GB。

**要跑矩阵，必须先腾出至少 2.5GB 显存 + 12GB 内存。** 这需要用户决定关哪些应用——关 Edge / 剪映 / QQ 会影响用户当前正在做的事，不能替他做主。

**副产物（有价值的确认）**：`\GPU Process Memory(*)\Dedicated Usage` 按 `pid_XXXX` 实例取进程级显存，在 WDDM 驱动模式下确实可用——这是 Windows 上唯一能拿到进程级显存的路径，`nvidia-smi` 在此模式下返回 N/A。本底账第 3.2 节的判断由实测证实。

**5. Ollama 实测口径（影响矩阵设计）**

- 推理发生在 `ollama` 主进程内，**没有独立 runner 子进程**（Ollama 0.35.1）。
- 1.7B 全 GPU（`num_gpu=99`）时，该进程 CPU 累计仅 0.48s / 5s 窗口 ≈ 10%，**CPU 几乎不参与** → 在这个组合下 CPU 优先级调度**没有作用对象**，必然测出"调度无效"。
- 同一轮 `load_duration` 高达 **33.6 秒**，说明模型加载受磁盘 I/O 支配，**I/O 是比 CPU 优先级更硬的变量**。

结论：矩阵必须用**分层部署的大模型**（GPU + CPU 同时干活），小模型全 GPU 组只能验证链路、不能证明调度价值。
