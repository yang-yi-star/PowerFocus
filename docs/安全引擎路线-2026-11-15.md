# PowerFocus 安全引擎路线 — 2026-11-15 实测记录

> 本文所有数字均为本机实测（2026-11-15 00:46–01:30 CST），不做估算。
> 结论一句话：**"吸收上游情报造自己的杀毒"技术可行，但在中国网络环境下病毒库分发是死结；可行的形态是"自有引擎 + 自建库镜像"，不是"复制一个卡巴斯基"。**

---

## 一、术语纠正

| 用户用语 | 业内正确说法 | 为什么不能用错 |
|---|---|---|
| 蒸馏其他 | **签名库聚合（signature aggregation）/ 多引擎编排（multi-engine orchestration）** | 蒸馏（distillation）专指把大模型的行为压进小模型，与杀毒引擎无关。用错词会导致方案沟通时被当成"AI 模型压缩" |
| 吸收他们的病毒库 | **接入上游情报源（upstream intelligence feed）** | 病毒库是签名集合，接入是数据层面；"吸收"含混，接不了 KSN 这类信誉云 |
| 造一个属于自己的卡巴斯基 | **构建自有签名扫描引擎** | 卡巴斯基是品牌+25年启发式积累+全球样本网+内核驱动，不可复制；能造的只有"签名匹配引擎" |

## 二、能造什么、造不出什么

### 2.1 能拼出来的自有引擎（全部合法许可）

| 层 | 开源件 | 许可 | 声称能力 |
|---|---|---|---|
| 签名匹配 | ClamAV 引擎（clamscan/clamd）+ main/daily/bytecode 三套 CVD | GPL-2.0 | 已知恶意软件检出，公开测试约 75–85% |
| 规则分类 | YARA / YARA-X | BSD-3-Clause | 家族特征、webshell、勒索家族规则 |
| 行为 | 自研规则引擎 | 自有 | 场景定制（下载落地、AI 生成物、MCP 出错产物） |
| 信誉 | 自建哈希库 | 自有 | 二次扫描秒判、白名单 |

### 2.2 造不出来的部分（差距不在签名库）

1. **启发式引擎**：卡巴的静态泛化能力是 25 年 PE 异常样本沉淀，无法从任何开源件拼出。
2. **内核驱动级行为拦截**：卡巴靠 KLIF/KLMD 驱动实时拦截文件/注册表/进程操作。这一层本机实测已经证明是**最大障碍**——KVRT 的 KLIF 驱动在本机零注册，引擎直接初始化失败（详见 `仓库全量盘点-2026-11-15.md` 第 8.2 节）。
3. **全球信誉云（KSN）**：几十亿样本的实时信誉查询，商业不开放，只能自建小规模替代。

### 2.3 结论

自造引擎的查杀率天花板约 **75–85%**（ClamAV 公开数据）。卡巴斯基 99%+。
**它不是卡巴的替代品，是卡巴的保底层。** 定位必须说清楚，否则对外宣传就是虚假陈述。

## 三、三个硬约束（必须一次说清，不能只挑好的讲）

### 3.1 约束一：网络分发（本次实测最致命）

| 源 | HTTP | 实测速度 | 判定 |
|---|---|---|---|
| npmmirror（国内 CDN 基线） | 206 | **3027.5 KB/s ≈ 3.0 MB/s** | 本机带宽正常 |
| ClamAV 官方站 `www.clamav.net` | 206 | **9.5 KB/s** | 引擎 215MB 需约 6 小时 |
| **`database.clamav.net` 病毒库（无 UA）** | **403 Forbidden** | — | **防盗链**，非网络封锁 |
| **`database.clamav.net` 病毒库（带 `User-Agent`）** | **200** | **6,143,991 B 完整取回** | **`freshclam` 自带 UA → 国内可正常拉库** |
| 清华 TUNA 镜像 `/clamav/` | 无有效响应 | — | 该路径未提供 ClamAV 库镜像 |
| GitHub Release | 连接失败 | — | 不可用 |

**判定（已修正）**：病毒库分发**不是死结**。`database.clamav.net` 的 403 是防盗链（拒绝无 UA 的裸请求），带上 `User-Agent: ClamWin/0.103 (Windows)` 后返回 **200 且完整取回 6.1 MB 的 daily.cvd**。`freshclam` 本身就会发送 UA，因此**在国内可以正常更新病毒库**。

真正慢的只有**引擎本体**：官方站实测 9.5 KB/s，215 MB 需约 6 小时。引擎是一次性下载，可接受；病毒库是周期性小文件（daily.cvd 6.1 MB），在带 UA 的链路下可用。

**因此 3.1 的结论从"不可用"降级为"引擎首次下载慢，病毒库正常"**。原"必须自建镜像"的判断不再成立——自建镜像是优化项，不是必需项。

### 3.2 约束二：体积

- ClamAV Windows x64 引擎包 **214.1 MB**（MSI）/ **215.4 MB**（zip）
- 三套病毒库合计约 **150 MB**
- 合计约 **365 MB**

E 盘剩余 39.7 GB，单机可承受；但**绝不能打包进主程序 exe**（当前 exe 19.5 MB，膨胀 18 倍不可接受）。
正确做法：走仓库已有的 `dependency_bootstrap.py` 按需下载（该模块已实现 下载→官方校验→落盘→artifact.json 完整链路），或首次使用时引导安装。

### 3.3 约束三：WSC 注册（"被 Windows 识别为杀毒软件"）

用户要求"应用本身也被识别为杀毒软件"。实测与文档口径：

- WSC（`root\SecurityCenter2` 的 `AntiVirusProduct`）**不是写注册表就能生效**。注册表硬写会被 Defender/Security Center 纠正移除。
- 正规路径需要：**EV 代码签名证书 + 微软的 AV 厂商认证流程**。这是钱 + 时间的硬门槛，一年数千元起，且有审核周期。
- 未通过认证而声明"系统级杀毒软件"，属于虚假宣传，且有被微软拉黑风险。

**判定**：WSC 注册是"可选项"，不是"免费步骤"。在产品未取得认证前，只能对外表述为"内置文件扫描"。

## 四、三层架构（推荐形态）

```
第一层 用户已有 AV（可选，不依赖）
    ├─ 探测：WMI root\SecurityCenter2\AntiVirusProduct（engine_adapters.py 已实现）
    ├─ 本机实测：WSC 有 2 条注册，但没有一条可用——
    │    · 腾讯电脑管家系统防护：注册路径 C:\Program Files (x86)\Tencent\QQPCMgr\18.2.30648.204\QQPCMgr.exe
    │      → exe 不存在，整个 QQPCMgr 目录不存在，Tencent\ 下仅剩 QQ / Qzone / QzoneMusic（陈旧注册）
    │    · Windows Defender：productState 0x062100（位解析为关闭+过期），
    │      WinDefend 与 WdNisSvc 均 Stopped + Manual，AntivirusSignatureVersion 为空
    ├─ 卸载表：无卡巴斯基
    └─ 判定：名义上有 2 个 AV，实际 0 个可用引擎（裸奔）
       → 这是"第一层不能当主体"的直接证据：用户机器的 AV 状态不可信，必须自有第二层

第二层 自有引擎（产品默认，本路线的主体）
    ├─ ClamAV 引擎 + CVD 库（GPL-2.0，独立进程调用 → mere aggregation，闭源产品亦可合法分发）
    ├─ YARA-X 规则（BSD-3）
    └─ 只扫"新落地文件"：下载的文件、AI 生成的文件、MCP 出错时的临时文件
        （不做全盘常驻扫描：ClamAV 全盘慢，且风险入口就是新落地文件）

第三层 产品内沙箱与判定
    ├─ 沙箱：文件先在隔离目录落地，扫描通过才交给用户/AI 使用
    ├─ 判定：_judge_scan() 五档（clean / threats / inconclusive / failed / timeout）
    └─ 原则：绝不把「退出码 0」当作「无威胁」——KVRT 事故的核心教训
```

### 为什么第二层只扫新落地文件

- 用户原话："下载文件的时候自动扫一下新文件，或者 AI 用 MCP 出错时扫一下"——这正好是新落地文件场景。
- ClamAV 全盘扫描性能差（本机 KVRT 历史全盘 6943 对象用了 366 秒；ClamAV 更慢）。
- 全盘扫描需要引擎强 + 库全 + 驱动级实时拦截，那正是造不出来的部分。**认清能力边界，只做能做的**。

## 五、三条可选路线

| 路线 | 内容 | 技术可行 | 分发可行 | 成本 | 查杀率 |
|---|---|---|---|---|---|
| **A 纯自有引擎** | ClamAV 全套，用户自行 freshclam | ✅ | ✅ 库可下（带 UA）；引擎首下慢 | 零 | 75–85% |
| **B 自有引擎 + 自建库镜像** | A + 自建 cvdupdate 私有镜像 | ✅ | ✅ 加速 | 一台轻量服务器 + 带宽 | 75–85% |
| **C 纯调度器** | 不造引擎，只调用系统已有 AV | ✅ | ✅ 零分发 | 零 | 取决于用户机器（本机为 0） |

**判断（已修正）**：
- A 可行。病毒库 403 已证为防盗链，带 UA 即可 200；`freshclam` 自带 UA。唯一代价是引擎首下约 6 小时（一次性）。
- B 从"唯一可行"降级为"可选加速项"——规模做大后再投入。
- C 不可行作为主体：本机 WSC 两条注册全是僵尸，实际 0 个可用引擎。**不能指望用户机器的 AV。**
- **推荐 A 作为起步，B 作为规模化后的优化。**

## 六、当前未决事项

1. **是否接受 75–85% 的查杀率天花板**（而非宣传成"卡巴级"）。
2. **是否需要自建病毒库镜像**（实测证明非必需，规模化后再考虑）。
3. **是否采购 EV 证书并走微软 AV 认证**（决定能否注册 WSC / 能否对外称"杀毒软件"）。
4. **v0.11 是否改 `DATA_SLOT`**：当前 `app_paths.py` 中 `DATA_SLOT = "v0.10"` 为硬编码，v0.11 建出后会继续共用 `%LOCALAPPDATA%\PowerFocus\v0.10` 的数据槽，与"每版独立"的 A 策略在数据层不一致。改则影响正在运行的 v1.00 产品。
5. **腾讯管家的僵尸注册清不清理**（删 WSC 注册属改系统状态，需明确授权；不清理不影响自有引擎，只影响"借用第一层"的判断）。

## 八、GPL 合规要点（比技术更先要确认的）

ClamAV 是 **GPL-2.0**。闭源商业产品要用它，只有一条安全路径：

- ✅ **以独立可执行程序调用**（`clamscan.exe` / `clamd.exe` 作为子进程），不 link `libclamav`，不静态编译进自己的二进制。
  → 属于 GPL 的 **"mere aggregation"（单纯聚合）**，不传染闭源主程序。
- ❌ 直接 `ctypes` 加载 `libclamav.dll` 或把它编译进 exe → 视为衍生作品，主程序必须 GPL 开源。
- ❌ 修改 ClamAV 源码后分发而不开源 → 违反 GPL。

**PowerFocus 必须走第一条**：`subprocess` 调 `clamscan.exe`，与现有 `kvrt_bundle.py` 调用 KVRT 的方式一致。
`clamav-rs` / `clamd` Python 模块这类 binding 属于链接库，**不可用于闭源产品**。
