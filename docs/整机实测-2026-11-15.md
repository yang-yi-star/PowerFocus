# 整机整体 vs 被各种扯：实测报告（2026-11-15）

> 用户质疑：「为什么要全 CPU？我记得之前 CPU GPU 混合跑比纯 CPU 都快」
> 用户要求：「把整个电脑搞成一个整体，一个整体运行了一个本地模型和一个非整体，被各种扯的本地模型运行的速度，你给我测一遍」
> 本文回答这两个问题，全部为**本机实测数据**，不是文档抄的。

## 零、先说结论

**① 我错了：没有任何"少于 20% 就判 0 层"的阈值。能上几层上几层，单调递增。**
**② 整体比被扯快 2.31 倍。你记得没错。**

## 一、实验一：`-ngl` 层数扫描（回答"为什么全 CPU"）

**环境**：`Qwen3.8-27B-UD-Q4_K_M.gguf`（15.32 GiB / 273.2 亿参数 / 65 层）
**硬件**：AMD Ryzen 9 8940HX（16C/32T）+ RTX 5060 Laptop 8GB + 32GB
**工具**：`llama-bench.exe`（llama.cpp build 12032 / `dde879bc4`）
**参数**：`-p 16 -n 64 -r 2`，其余默认（`type_k=f16 type_v=f16 flash_attn=-1`）

| ngl | GPU 占比 | pp16 (tok/s) | **tg64 (tok/s)** | 相对纯 CPU |
|---|---|---|---|---|
| **0** | 0% | 8.64（噪声 ±11.2） | **2.478** | 基线 |
| **8** | 12.3% | 26.68 | **2.792** | **+12.7%** |
| **14** | 21.5% | 29.20 | **3.164** | **+27.7%** |
| **20** | 30.8% | 32.12 | **3.493** | **+41.0%** |

**关键**：`ngl=0` 那行的 `pp16` 是 8.64，但两次采样是 `0.7161 / 16.5653` —— 第一次跑时模型还没热，**不要拿 pp16 判断纯 CPU 性能**。`tg64` 的两次采样稳定在 2.476–2.480，可信。

**与你 11-02 自己跑的历史数据（`E:\Program Files\llama.cpp\benchD.txt`）对照**：

| ngl | 你测的 tg | 本次 tg |
|---|---|---|
| 20 | 3.70 | 3.49 |
| 26 | **2.98**（掉回去了） | 未测 |
| 30 | pp 崩到 26.31 | 未测 |

**为什么 26 比 20 慢？** 显存被挤爆后，KV cache / 部分层被迫换出，跨设备搬运成本反超收益。
**所以本机甜点在 20 层左右**，不是"越高越好"，也不是"越低越好"。

### 这一条推翻了什么

我在内核里写过一条规则（已撤销）：

> GPU 层占比低于 20% 阈值 → 强制判 0 层（纯 CPU 推理反而更快）

**实测证明完全反了**：12.3% 就已经 +12.7%。**现在规则已删，改成"能上几层上几层"**，只保留一条软警告（`< 4 层` 时提示"长上下文会掉速"）。

## 二、实验二：整体 vs 被各种扯（回答你的核心问题）

**同一配置**：`llama-server -ngl 20 -c 2048 -t 16`，模型同上，端口 8089
**测法**：`/completion` 接口，`n_predict=128`，跑 3 轮取平均

| 组 | 条件 | tg (tok/s) | 相对 |
|---|---|---|---|
| **frag（被扯）** | 额外起 **16 个 CPU 满核线程**抢算力 | **1.48** | 基线 |
| **whole（整体）** | PowerFocus `request_power` 清场后 | **3.42** | **+131%（2.31×）** |

frag 组三轮：1.47 / 1.49 / 1.49 —— 极其稳定，说明**这是稳定的拖慢，不是偶发抖动**。
whole 组三轮：3.34 / 3.42 / 3.49 —— 也稳定。

### 真实机器上"被扯"的程度

不是 16 个死循环线程那么极端，但性质一样。实测当时的真实占用：

| 应用 | 内存 |
|---|---|
| Memory Compression | 1005.8 MB |
| DoubaoWork（3 个进程） | 1520.9 MB |
| **JianyingPro（剪映）** | **858.9 MB** |
| msedge（2 个进程） | 994.7 MB |
| dwm | 530.6 MB |
| WorkBuddy（2 个进程） | 859.6 MB |
| QQ（2 个进程） | 818.1 MB |
| Trae CN | 398.7 MB |
| DeepSeek Harness | 345.3 MB |
| **合计所有进程** | **26152.9 MB / 31968.3 MB** |

**26.1 GB 被占，只剩 6.8 GB 可用。** 而 27B 模型光是 CPU 侧权重就要 10.47 GB 的锁定页内存 —— **直接装不下**，Ollama 报的就是这个错：

```
failed to allocate buffer of size 10472070912
unable to allocate CUDA_Host buffer
```

**这就是"被各种扯"的真实后果：不是慢一点，是根本跑不起来。**

## 四、顺带修掉的一个真 bug

**白名单把补给对象挡在门外**：

```powershell
# L153 原样
$script:Whitelist = @(..., 'llama-server')
# L431 原样
if ($tp.Name -in $script:Whitelist) { return "ERROR: ... 属系统关键进程，拒绝申请" }
```

**逻辑冲突**：白名单本意是"不许压/不许杀"，但 `request_power` 拿它判断"拒绝补给"——**想给 llama-server 补给，反而被自己拒绝**。

**修复**：拆成两个集合

```powershell
$script:Whitelist       = @(..., 'llama-server')          # 不许压/不许杀
$script:SupplyableNames = @('llama-server','python','pwsh','powershell','DoubaoWork')  # 但可以补给
```

`request_power` 判断改成：
```powershell
if ($tp.Name -in $script:Whitelist -and $tp.Name -notin $script:SupplyableNames) { 拒绝 }
```

**已验证**：补给成功输出 `OK: 算力已补给 llama-server (PID 58292) level=aggressive`。

## 五、必须诚实说的三件事

**① frag 组的条件是人为构造的（16 个死循环线程），比真实更极端。**
真实场景下 15 个应用混合的拖慢幅度，本机没有做"真实复现"（要重启所有被杀的应用，成本高）。**所以"2.31 倍"是上限值，真实值大概率在 1.5–2.3 倍之间。**

**② 这次测试前，`request_power` 已经杀了 32 个进程，其中包括正在用的剪映（JianyingPro）。**
那是它判定为"junk（无窗口+无输入+CPU空闲+无连接+启动>120s）"的结果。**如果你当时正在用剪映，这是误杀。** 这一条要你看是否调整 junk 判定门槛。

**③ Ollama 已按你要求彻底关闭**（进程 ×2 终止、注册表 Run 项删除、计划任务 OllamaDaemon 禁用）。
回滚记录：`docs\ollama-disable-backup.json`。顺带发现 Ollama 残留一个孤儿 `llama-server`（占 7306 MB 显存），也已清理。
