# 统一内存接线 — 任务 1 实测记录（2026-11-15）

> 让它从"死资产"变成"命令总线可调用的能力"。不搬启动器，不造新接口。

## 二、移植边界：搬算法，不搬启动器

原文件里还有 `Start-UnifiedMemoryMode` —— 那是 **llama-server 的启动器**（拼命令行、拉起 `llama-server.exe`、设 `127.0.0.1:8080`、看门狗）。

**不搬它的理由**：接进内核会把 PowerFocus 变成"llama.cpp 的外壳"，而用户对产品的定义是**通用型算力调度中心，给任何电脑、任何服务器用，不绑定某一个推理框架**。启动器是"一个应用场景的实现"，不是"算力池本身"。

所以只搬四段纯计算：
| 函数 | 作用 |
|---|---|
| `Get-GpuMemoryInfo` | 调 `nvidia-smi` 拿显存 total/used/free |
| `Get-SystemMemoryInfo` | CIM 拿物理内存 total/available |
| `Get-GgufLayerCount` | GGUF v3 二进制头解析，读出模型层数 |
| `Calculate-OptimalLayerSplit` | 算 GPU 层 / CPU 层 |

外加一个新组合函数 `Get-UnifiedMemoryPlan`，把上面四段串成"一次调用给出整机算力现状 + 层分配建议"。

## 三、可移植性改造：拆掉 8GB 硬编码

原实现里有一行：

```powershell
$script:MaxGpuLayersSafe = 20
```

注释写着"8GB 显存机 = 20 层"。这是 **RTX 5060 Laptop 8GB 的实测经验值**，写死在内核里意味着：
- 更大的机器（24GB / 48GB 显存）被错误压制到最多 20 层
- 更小的机器（4GB）反而没有保护

**改成**：

```powershell
$script:MaxGpuLayersSafe = 0   # 0 = 按显存自动推导；>0 = 硬钳
```

- `0`（默认）：完全按 `floor(可用显存 / 每层大小)` 推导，适配任意机器
- `>0`：硬钳到该值，8GB 机器若实测 OOM 可显式改回 20

**另外两个预留量的语义也写清了**：
- `CudaReservedMB = 512`：CUDA 上下文固定占用
- `ComputeReserveMB = 1024`：计算缓冲区 / 驱动 / 显示合成预留

这两个不是"给别的应用留空间"，而是"给显卡自己留活路"。用户要求的"给其他应用最小空间、给模型最大空间"是调度层的事（进程优先级 + 电源 + I/O），不在层分配公式里。**这一点不能混。**

## 四、实测抓到的两个真 bug（不跑就发现不了）

### bug 1：单卡机器返回形状错，层分配直接算成 0

`Get-GpuMemoryInfo` 用 `$result += @{...}` 累加，函数 `return $result` 时，PowerShell 会**把单元素数组解包成单个 hashtable**。

后果链：
1. 单卡机器 `$gpu` 变成 hashtable（不是数组）
2. `$gpu[0]` → 在 hashtable 上取 key `"0"` → 拿到 `$null`
3. `$gpu[0].FreeMB` → `0`
4. `usable = 0 - 512 - 1024 = -1536` → 被归零
5. **层分配结果 = GPU 0 层，静默错误，不报错**

这台机器只有一张卡，第一次实测就命中了。

### bug 2：修 bug 1 时引入双层嵌套

第一版修法用 `return ,$result`（前置逗号），单卡能读到了，但 JSON 变成：

```json
"gpu": [ [ { "Index": 0, ... } ] ]
```

`return ,$result` 在外层又套了一层数组。单卡靠 PowerShell 的成员枚举侥幸能读到值，**多卡机器上 `$gpu[0]` 拿到的是内层数组**，层分配会算错。

第二版修法用 `$gpu = @(Get-GpuMemoryInfo)`，`@()` 又把 `-NoEnumerate` 的输出当成单个对象包了一层，**还是双嵌套**。

**最终正确写法**：

```powershell
# 函数内
Write-Output -NoEnumerate $result

# 调用方
$gpu = Get-GpuMemoryInfo     # 不加 @()
```

`-NoEnumerate` 原样输出数组，既防单元素解包，又不多套一层。

## 五、环境坑：shell 工具进程是 PowerShell 5.1，不是 7

这台机器上 PowerShell 工具默认跑的是 **`5.1.26100.9711`**，而内核第一行有 `#requires -Version 7.0`。

直接在主进程里 dot-source 会报：

```
无法运行脚本…因为该脚本包含用于 Windows PowerShell 7.0 的 "#requires" 语句
```

**结论**：所有涉及内核的操作，必须显式用子进程：

```powershell
& C:\Tools\PowerShell7\pwsh.EXE -NoProfile -File <脚本>
```

这条与用户 AGENTS.md 第 23 条"pwsh 7+ 唯一，禁 powershell.exe 5.1"完全一致。

## 六、实测数据（2026-11-15 01:12，本机）

**硬件**：RTX 5060 Laptop 8GB + 32GB 内存 + Ryzen 9 8940HX

| 项目 | 实测值 |
|---|---|
| 显存 total / used / free | 8151 / 6061 / **1839 MB** |
| 系统内存 total / available | 31968.3 / 3888.6 MB |
| 模型 | `Qwen3.8-27B-UD-Q4_K_M.gguf` 15701.71 MB |
| GGUF 解析层数 | **65 层** |
| 每层大小 | **241.56 MB** |
| 可用显存 | 1839 − 512 − 1024 = **303 MB** |
| **层分配结果** | **GPU 1 层 / CPU 64 层** |

**这个结果说明什么**：27B 模型在 8GB 显存上只能塞 1 层进 GPU，其余 64 层全在 CPU。这不是算法错，是物理限制——**也再次证明"四格矩阵实验"在这台机器上跑不动**，因为显存余量连 2 层都放不下（每层 241MB，可用只有 303MB）。

**端到端输出**（走命令总线）：

```
OK: GPU层=1 CPU层=64 总层=65 -> E:\PowerFocus\versions\v0.11\commands\out\unified-plan.json
```

落盘文件 612 字节 / UTF-8 BOM / 中文正常 / `"gpu": [ {...} ]` 单层。
