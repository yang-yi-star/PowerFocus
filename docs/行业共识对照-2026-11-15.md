## 二、行业共识，但我们没做（按价值排序）

### ① 【最高价值】部分 offload 会让 KV cache 跨设备，长对话反而变慢

**共识**（llama.cpp 官方 + 多篇实测）：

> "A common 'slow long-context' failure is loading only some layers to the GPU so that the KV cache ends up straddling GPU and CPU, forcing data movement on every decode step."

**KV cache 跟着层走**：第 l 层的 KV cache 存在第 l 层所在的设备上。
部分 offload → 一部分 KV 在 GPU、一部分在 CPU → **每个 token 生成都要跨 PCIe 搬数据**。

**我们的现状**：8GB 卡跑 27B 模型，算出 "GPU 1 层 / CPU 64 层"。
**这是最坏配置**——1 层 KV 在 GPU、64 层在 CPU，全程跨总线。

**标准解法**（llama.cpp 官方给的三个选项）：
- 全 offload（`-ngl 99`，显存放不下就别想）
- `--no-offload-kqv`：K/Q/V 张量全留 CPU，其余跑 GPU（省显存换速度）
- **要么 0 层全 CPU**：慢但稳，不跨总线

**对我们的意义**：`Calculate-OptimalLayerSplit` 算出 1 层就上 GPU，**不如算 0 层**。
需要增加一条规则：**当 GPU 层数 < 总层数的 20% 时，判为"不值得 offload"，直接 0 层**。

**✅ 已实装**（内核 `Calculate-OptimalLayerSplit` 尾部）：阈值 `$minLayerRatio = 0.20`，
低于就强制 0 层并写 `Warn` 说明。实测本机 27B 模型（65 层）算出 8 层 = 12.3% < 20%，
**已判 0 层**，输出 JSON 带 `Warn` 字段说明原因。

### ② 【高价值】llama.cpp 自带 `--fit`，我们在重造轮子

**共识**：llama.cpp 2025 起 `--fit` 默认开启，自动按显存 sizing 层数与 context。

**我们的现状**：`Calculate-OptimalLayerSplit`（724 行）手算。
风险：我们的算法与 `--fit` 冲突，两边各算一次，结果不一致。

**标准做法**：要么**不传 `-ngl`，让 `--fit` 自己算**；要么**接受我们的算法但显式 `--fit off`** 避免打架。

### ③ 【高价值】KV cache 量化 `--cache-type-k/v q8_0`，能砍一半 KV 显存

**共识**：

> "Moving from `f16` to `q8_0` roughly halves the KV cache memory for a modest quality cost."

**我们的现状**：`model-profiles.json` 里有 `cache_type_k` / `cache_type_v` 字段（boost 时读），但**没有在统一内存规划里用它**。

**意义**：开 q8_0 能省下相当于 +1~2 个 GPU 层的显存。对 8GB 卡是实打实的收益。

### ④ 【高价值】Job Object 硬 CPU 上限，我们没有

**共识**：Windows Job Object 支持
- `JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP`（硬上限，永不超）
- `JOB_OBJECT_CPU_RATE_CONTROL_SOFT_CAP`（软上限，机器空闲时可超）

**我们的现状**：全靠 `Process.PriorityClass` 抬/压 —— **优先级只影响抢 CPU 的顺序，不限制总量**。
一个高优先级进程照样能把 32 个核全吃满。

**意义**：这是"给其他应用最小空间"的**唯一硬手段**。优先级是软的。

### ⑤ 【中价值】CPU Sets 是"软亲和"，`SetProcessAffinityMask` 是"硬亲和"

**共识**（Microsoft 原文）：

> "CPU Sets provide APIs to declare application affinity in a 'soft' manner that is compatible with OS power management."

**我们的现状**：`set_affinity`（1880 行），需确认用的是 `SetProcessAffinityMask`（硬）还是 CPU Sets（软）。

**KomuraSoft 的六条原则里第 3、4 条直接点名**：
- "Consider affinity near the end. Affinity is a strong setting."
- "Do not hardcode P-cores/E-cores, observe them. Hardcoding CPU numbers is dangerous."

**意义**：用户机器是 16C/32T 的 Ryzen 9 8940HX，同构核。但产品要"给各种电脑用"，异构核（Intel P/E）上硬亲和会踩坑。

### ⑥ 【中价值】Windows QoS 有七档，我们只用了 Eco

**共识**：High / Medium / Low / Utility / Eco / Media / Deadline。

我们用了 High（通过 PriorityClass 间接）和 Eco（`set_ecoqos`）。
`Media` / `Deadline` 是多媒体调度器专用，不适用。

**但 `Utility`（Windows 11 22H2 引入）** 对后台服务更合适——比 Eco 语义更准。

### ⑦ 【中价值】`--parallel` 每 slot 单独分配 KV cache

**共识**：

> "Setting `--ctx-size` per-request expectation instead of per-slot — it's allocated per slot, so `--parallel 8` at `--ctx-size 8192` reserves cache for all 8 slots at that size."

**我们的现状**：boost 时传 `Ctx`，**没传 `--parallel`**。
llama-server 默认 `--parallel 1`（llama.cpp 近年默认），但如果用户在 `model-profiles.json` 里配了上下文，实际 KV 占用可能是 ctx × parallel。

### ⑧ 【低价值】mmap 加载让多进程共享权重

**共识**：llama.cpp 用 mmap 加载，模型文件是被分页进内存而非复制。
意义：多个 llama-server 实例可共享同一份权重页。

我们没利用，但单模型场景下价值不大。

## 三、一句话总结

**最高优先级的三件事**：
1. **算出 GPU 层数 < 20% 时强制 0 层**（避免 KV cache 跨设备，现在是 1 层反而最慢）
2. **别和 `--fit` 打架**（要么让它算，要么显式关掉）
3. **利用 `--cache-type-k/v q8_0`**（省一半 KV，等于多 1–2 层）

**根因**：我们现在**只算"权重放哪"，没算"KV cache 放哪"**。
而 KV cache 才是长对话变慢的真凶——权重是静态的，KV 是随 context 线性涨的。
