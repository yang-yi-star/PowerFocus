## 零、先认错：上一轮的判据是错的，而且错在两个相反方向

用内核自己的判据在**同一台机器、同一时刻**扫当前所有进程（`tools\probe-ranks.ps1`），结果和我上一轮的结论完全不符：

| 等级（旧判据） | 个数 | 合计内存 |
|---|---|---|
| protect | 22 | 5,083 MB |
| task | 15 | 2,475 MB |
| semi | 2 | 138 MB |
| **junk** | **1** | **83 MB** |

**只有 1 个 junk（MSPCManagerCore 83MB）。** 也就是说「上一轮补给杀了 32 个进程」不是判据稳定得出的结果，而是当时那批进程状态不同造成的偶然。判据本身不稳。

更关键的是两个反向错误同时存在：

1. **`task` 判得太宽**：只要「有窗口祖先」就算 task → 完全不动。QQ、剪映、WorkBuddy、Trae、Edge 全被打成 task/protect，**等于根本没清场**。你说的「没点开的收走算力」，旧判据一条也收不走。
2. **`junk` 判得太狠**：直接 `Stop-Process -Force`。剪映有可见窗口只是最小化，一旦父进程链断掉就可能滑进 junk → **误杀有未保存工作的应用**。

## 一、按你的口径重写：判断「用没用」只看后台窗口

你给的标准是**看后台有没有点开**，不是分析进程自身指标。据此重写为五档：

| 等级 | 判据 | 处理 |
|---|---|---|
| `protect` | 自身 / 系统关键 / 白名单 / 授权 / Windows 服务 / DeepSeek | **完全不碰** |
| `active` | 前台窗口所属进程 | **完全不碰** |
| `busy` | **CPU 真在动**（导出/训练/编译/渲染） | 不压（压了会拖慢正在干的活） |
| `visible` | **有可见窗口（含最小化）**，或属于某可见窗口应用的子进程 | **降优先级，绝不杀** |
| `idle` | 无窗口 + CPU 不忙 + 不属于任何可见应用 | **降优先级 + EcoQoS + 修剪工作集，绝不杀** |

### 关键修正：TCP 连接不再算「在用」

旧判据把「有 TCP 连接」当作在干活。实测结果：**QQ、剪映、WorkBuddy、Edge 全部因为「挂着服务器连接」被判 busy → 完全不动**。它们只是挂在后台连服务器，根本没在跑任务。

改法：**只有 CPU 真在动才算 busy；TCP 只用于展示，不参与分级。**

### 第二处修正：最小化窗口要能识别

旧判据用 `MainWindowHandle` 判断有没有窗口。最小化窗口的该值可能为 0。现在改成**枚举所有可见窗口（含最小化）得到 PID 集合**，再用它兜底。

## 二、铁律：清场永不杀进程

代码里清场段现在**一条杀进程语句都没有**（`Stop-Process` 在清场范围内已清零，只剩显式 `kill_process`/`uninstall_app` 两个 action 里还有）。

依据是你自己的话：**「本质上就是给其他应用最小的空间，给他最大的空间」**——是压缩空间，不是杀掉。

杀进程会丢未保存的工作（剪映 858.9MB 那次就是这么被误杀的）。而「最小空间」用这三样就够：

1. **降优先级**：`Normal`/`AboveNormal` → `Idle`（aggressive/godmode）或 `BelowNormal`
2. **EcoQoS 效率模式**：`PROCESS_POWER_THROTTLING_EXECUTION_SPEED`，把进程限制到能效频率档
3. **工作集换出**：`EmptyWorkingSet`，把物理页换到磁盘

而且**释放时三样全部还原**：优先级写回原值、EcoQoS 逐个关闭。

## 四、抓到的两个真 bug（都已修）

### bug 1：哈希表用 `+=`，异常被 catch 吞掉

```powershell
$script:PowerEcoQos += $p.Id      # PowerEcoQos 是 @{} 哈希表，+= 会抛异常
```

后果：EcoQoS 每次都「成功」但计数永远 0，被 `catch {}` 静默吞掉。第一次实测返回「EcoQoS 0 个」就是这个。

改法：`$script:PowerEcoQos[[int]$p.Id] = $true`。改后实测 13 个生效。

### bug 2：打包脚本写死 `versions\v0.10`

`build\build.ps1` 第 13 行：

```powershell
$V010 = Join-Path $Repo 'versions\v0.10'
```

后果：**每次打包都把这 5 个 Python 组件（`app_paths`/`dependency_bootstrap`/`kvrt_bundle`/`engine_adapters`/`security_scan`）的旧副本塞进 exe**。于是「内核指针已经指到新版本、exe 里跑的却是旧组件」——这是「一直在用旧版」的第二层原因，比进程占端口那层更隐蔽。

改法：跟随 `versions\current.json` 解析，指针缺失时退回「含这些组件的最高版本目录」。打包输出已确认：

```
打包用的组件目录: E:\PowerFocus\versions\v0.12
```

## 六、第三次自我撤回：`/api/health` 中文「乱码」不是乱码

我此前一直把「`/api/health` 的 `name` 显示 `ç”µè„...`」记成待修 bug。

实测（`tools\check-health-encoding.py`）：

```
Content-Type = application/json
原始字节前 40 = b'{"app":"ok","name":"\xe7\x94\xb5\xe8\x84\x91\xe7\xae\x97...'
按 UTF-8 解码 = {'name': '电脑算力调度中心', 'kernel_version': 'v0.12', ...}
```

响应体是**标准 UTF-8**，`name` 就是「电脑算力调度中心」。

`ç”µè„...` 是 **PowerShell 的 `Invoke-WebRequest` 按 latin-1 解码**造成的显示假象。浏览器 `res.json()` 不做 charset 猜测，直接按 UTF-8 解析，显示正常。

**结论：不是 bug，代码不用改。这条待办撤销。**

## 八、还没做（明确列出，不藏）

1. **`--fit` 与自研 `Calculate-OptimalLayerSplit` 两个规划器会打架**——llama.cpp 自带 `--fit` 默认开启，我们又在自己算层数。未定是否直接透传 `--fit`。
2. **Job Object 硬 CPU 上限没做**——`JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP` 是「给其他应用最小空间」的唯一硬手段，现在只有优先级 + EcoQoS 这种软手段。
3. **KV cache 量化没启用**——`--cache-type-k/v q8_0` 能砍一半 KV 显存，`model-profiles.json` 有字段但规划里没用。
4. **`--parallel` 每 slot 独立 KV cache 没传**。
5. **`mcp\VERSION.json` 仍是 0.11.1**，`dist\PowerFocus-MCP-v0.11.1.zip` 未重打包（MCP 是独立版本线，要不要跟内核版本走未定）。
6. **这台机器上 `visible` 17 个共 2530MB 能不能真腾出算力给模型，还没做端到端 A/B**——上一轮「整体 vs 被扯」实测是 2.31 倍，但那是旧判据杀的 32 个进程，新判据只压不杀，收益需要重测。
