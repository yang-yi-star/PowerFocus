# 配套应用与链路组保护（v0.13）

日期：2026-11-15
版本：`versions\v0.13`（新建，转 stable）
触发原话：**「那你也要判断另一种形态，我 QQ 连的是我手机，然后 DSH 我用它在连着我的 QQ，然后用 DSH 里面的人跟我 QQ 聊天。其他几个的话都没在用，就这 QQ 和 DSH 在用，你这个都判断不出来。」**

---

## 零、先说结论：这个判断，代码判不出来，只能由你声明

我把四个能用的信号全测了一遍，全部失效。不是我没测，是这四个信号在你的场景下本来就不成立。

| 信号 | 实测值 | 为什么判不出「在用」 |
|---|---|---|
| **CPU** | QQ 13180 **0.8%**、QQ 20308 **0.4%**、DSH 48548 **0.4%**，其余全 0.0% | 聊天是 IO 密集不是 CPU 密集，你发一条消息 CPU 几乎不动 |
| **IO 速率** | 4 秒采样，**所有 QQ/DSH 进程读 0.0 KB/s、写 0.0 KB/s** | `Get-Process` 的 `ReadTransferCount`/`WriteTransferCount` **返回空**，`Get-Counter` 的 `IO Read/Write Bytes/sec` **恒为 0**。这条数据源在这个环境拿不到 |
| **TCP** | QQ 有 3 条外部 Established（`36.155.245.16:80`、`36.155.163.51:14000`、`223.109.208.252:443`）；DSH 有 3 条（`120.204.2.192:443` 等） | 只能证明「连着」。Edge 也连着 CDN 443、剪映也连着服务器——**挂着的应用一样有连接** |
| **窗口** | QQ 有窗口但最小化 | 只能证明「点开过」。QQ 最小化着照样在收发消息 |

**上一轮我把 TCP 从判据里删掉，就是因为「挂着的也连着」这条。但删过头了——QQ 的连接不是挂着，是活的。这两个结论并不矛盾：TCP 不能证明「在用」，也不能证明「没在用」。它没有判别力。**

所以「在用」这件事，在这个环境里**只能由你声明**。

而这不是临时补丁。你产品定义里本来就有这个词——**「尽可能把同时与那个本地模型搭配的另一个应用一起支持上，让他们更快的运转」**。这就是「配套应用」。

---

## 一、机制：配套应用清单

新增 `versions\v0.13\companion-apps.json`：

```json
{
  "apps": [
    {"name": "QQ", "reason": "手机 QQ 的消息通道。压低它会拖慢手机端收发"},
    {"name": "QQEX", "reason": "QQ 扩展进程（父进程是 QQ），属同一链路组"},
    {"name": "DeepSeek Harness", "reason": "DSH 通过 node 中转与 QQ 对话，是正在使用的核心链路"}
  ]
}
```

**按父子链聚合整组**：清单里点一个应用名，它和它的所有后代进程一起进 protect。实测这一条覆盖 **41 个 PID**：

- QQ：24 个进程
- QQEX：5 个进程（父进程是 QQ 5676 / QQ 13180）
- DeepSeek Harness：5 个进程
- 其余是这几棵树的附属子进程

判定顺序里配套应用排在**第二**位（只在自己之后）：

```
自身 → 配套应用组 → DeepSeek树 → 永不压名单 → 授权名单 → 系统关键 → Windows服务
     → 前台 → CPU忙 → 有窗口 → 有窗口祖先 → idle
```

清单文件缺失时兜底 `@('QQ','QQEX','DeepSeek Harness')`——宁可多保一条消息通道，也不能让你以为在跑全机清场结果把聊天压死了。

## 二、链路实测：DSH 到底怎么连 QQ

你说「DSH 连着 QQ」，实测的拓扑是这样：

```
DSH 43136 ──(127.0.0.1:52817 ↔ 127.0.0.1:3001)── node 49236
DSH 43136 ──(127.0.0.1:50736)── [DSH 内部 hub]
   └ 接收 39912 / 41596 / 39372 的多条回环连接
QQ 13180  ──(127.0.0.1:9210/4301/4310/4001)── QQ 内部 IPC
QQ 20308  ──(127.0.0.1:9211/4003)── QQ 内部 IPC
QQEX 5676 ──(127.0.0.1:9410)── QQEX IPC
```

**DSH 不是直连 QQ 的端口**，它连的是 `node`(PID 49236) 的 3001。node 同时连着 DSH 的 52817。所以链是 **DSH ↔ node**，QQ 那侧是独立的 IPC 体系。

DSH 和 QQ 的父进程**都是 `WmiPrvSE`(5288)**——说明两者都是被 WMI 拉起的，不是父子关系。

这意味着「DSH 连着 QQ」在你的使用方式上成立，但在**进程/网络拓扑上不成立**。所以靠拓扑自动推断这条路也断。

## 四、抓到一个真 bug：`$pid` 是只读变量

第一版改动写完，语法 0 错误，运行不报错，但 QQ 仍然是 visible。

根因：

```powershell
foreach ($pid in $ctx.NameMap.Keys) { ... }   # ✗
```

**`$PID` 是 PowerShell 的只读自动变量（当前进程 ID）**，用它当循环变量会抛：

```
无法覆盖变量 PID，因为它是只读变量或常量。
```

这个异常是非终止错误，被外层吞掉，**整个聚合循环静默失效**——一个不报错、不崩溃、只是不干活的 bug。

而 DSH 当时显示 protect，是因为它本来就在 `Get-DeepSeekTreePids` 里，**跟配套机制无关**——差点被这个假象骗过去，以为机制生效了。

改法：循环变量换名 `$cpid`。改后 `CompanionPids = 41`，QQ 与 DSH 全部 protect。

**这是本轮第二个「静默失效」类 bug**（第一个是哈希表 `+=`）。两个都是语法合法、运行不报错的。**

## 五、这条机制的边界（诚实列出）

1. **清单要你维护**。点一个应用名就保一棵树，但名字要对（`QQ` / `QQEX` / `DeepSeek Harness`，按进程名去掉 `.exe` 匹配）。
2. **它保护的是「不压」，不是「加算力」**。配套应用进 protect 意味着清场时不动它，但它不会因为被列为配套就获得额外算力。
3. **`node`(49236) 没进清单**。它是 DSH 与 QQ 之间的中转层，实测自身几乎不耗算力。如果哪天发现它成瓶颈，补进清单即可。
4. **「怎么自动建议候选」没做**。理想做法：扫「有外部 Established 连接 + 有可见窗口」的进程，提示「发现这些可能在用，要保护吗」。但这仍然会误报（Edge 也满足），所以现在只做声明，不做推断。
5. **这台机器的 `visible` 17 个、2,404 MB 能真腾出多少算力给模型，需要端到端 A/B 重测**——上一轮「整体 vs 被扯」的 2.31 倍是旧判据杀掉 32 个进程测出来的，只压不杀的数必须重测。
